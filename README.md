## 1. Архитектура и фундаментальные принципы

### 1.1 Сквозной конвейер данных (Data Pipeline)

Архитектура системы построена по модульному принципу с разделением ответственности на независимые слои:

```
[Источники] ──> [Сбор (L1 / L2)] ──> [Raw-кэш] ──> [Нормализация] ──> [Валидация] ──> [Матчинг атлетов] ──> [Расчет баллов] ──> [Рейтинг и UI]
```

1. **Реестр источников:** Конфигурация сайтов, типов соревнований, расписаний обхода и стратегий доступа.
2. **Сбор (L1/L2):** 
   - **L1 (HTTP/API):** Быстрый и ресурсоэффективный сбор через прямые HTTP-запросы (`httpx`, `requests`) к закрытым и публичным JSON API площадок, либо парсинг статического серверного HTML (`BeautifulSoup`, `lxml`, `selectolax`).
   - **L2 (Headless Browser):** Сбор страниц со сложным SPA-рендерингом (`Playwright`) в качестве резервного пути.
3. **Raw-слой (Кэш на диске и в БД):** Сохранение неизмененных исходных страниц/ответов API с контролем `content_hash` (SHA-256). Позволяет повторно перепарсить данные при смене логики без нагрузки на внешние сайты и без траты токенов.
4. **Нормализация:** Приведение разрозненных форматов к единому каноническому виду: миллисекунды времени, нормализованные дистанции ($\pm 2\%$), единые статусы финиша, чистка ФИО.
5. **Валидация данных:** Автоматический аудит протоколов по математическим инвариантам до сохранения в аналитическую базу.
6. **Матчинг и дедупликация:** Сопоставление строк протоколов с профилями реальных людей, выявление сотрудников Сбера.
7. **Рейтинговый движок:** Чистые детерминированные математические функции расчета очков без участия нейросетей.
8. **Интерфейс и ИИ-анализ:** Отображение витрины, карточек спортсменов, соревновательных квантилей и формулирование текстовых отчетов ИИ.

### 1.2 Принципы проектирования (указания куратора)

- **Минимизация расхода LLM-токенов:** Нейросети не используются для регулярного парсинга, сортировок или математических вычислений. LLM привлекается только для формулирования аналитических текстов по уже посчитанным метрикам или для синтеза адаптеров к новым нестандартным форматам в случае аварий.
- **Сначала схема данных, затем код:** Структура таблиц спроектирована до массового сбора, что гарантирует целостность связей между соревнованиями, дистанциями и участниками.
- **Масштабирование по правилу «1 $\to$ 10 $\to$ 100 $\to$ 1000»:** На каждом десятикратном увеличении выборки возникает около 10% нестандартных краевых ситуаций (инверсии времени, спринты с финалами, анонимные участники, двойные зачеты). Все они документируются и изолируются.
- **Отказоустойчивость и локальность:** Парсеры не падают при сетевых сбоях отдельных страниц, кэшируют ответы и устойчивы к блокировкам.

### 3.2 Автоматические проверки качества данных (6 инвариантов)

Каждая загруженная дистанция перед сохранением в базу проходит валидатор (`store.py`):
1. **Полнота выборки:** Число сохраненных записей совпадает с числом, заявленным организатором в заголовке протокола.
2. **Определенность пола:** Пол участников валиден (M/F). Анонимные чипы без ФИО («N.N.») отсеиваются от проверки пола.
3. **Наличие результата:** У всех участников со статусом `FIN` присутствует официальное время финиша.
4. **Непрерывность мест:** Места финишеров строго идут по порядку, начиная с 1, без пропусков.
5. **Монотонность времени:** Время финиша не убывает с ростом места. Сравнение производится строго по тому времени (чистому или пистолетному), по которому площадка рассчитывала места (`race.place_by`).
6. **Контроль статусов:** Все записи имеют валидный спортивный статус: `FIN` (финиш), `DNF` (сошел), `DNS` (не стартовал), `DSQ` (дисквалификация), `NC` (вне зачета), `LAP` (снят на круг).

### 3.3 Очередь проблем (`issue`)

Вместо плоского файла логов реализована реляционная очередь инцидентов (`issue`):
- Уникальный хэш инцидента (`fingerprint`) предотвращает дублирование записей об одной и той же проблеме, увеличивая счетчик `occurrences`.
- Жизненный цикл проблемы: `new` $\to$ `agent_working` $\to$ `proposed` $\to$ `approved` / `rejected` $\to$ `resolved` (плюс статусы `known` и `blocked`).
- Таблица `known_exception` изолирует особенности регламента, не являющиеся багами (например, стадионные спринты с финалами, где время победителя финала может быть больше лучшего времени предварительного забега).

## 4. Модуль сбора биатлонных протоколов (`parser_biathlon`)

### 4.1 Источники и структура файлов

1. **`biathlonrus.com` (Союз биатлонистов России):** Официальный календарь соревнований (Чемпионат России, Кубок России, Первенства, межрегиональные старты). Протоколы публикуются в формате PDF (создаются программами хронометража WSRP, Ski123, SIWIDATA).
2. **`base.biathlonrus.com`:** Официальный реестр спортсменов СБР (4 569 атлетов в формате CSV). Служит эталоном для верификации участников и разрешения коллизий OCR.

### 4.2 Технология гибридного распознавания (PDF + OCR)

В части протоколов (созданных через виртуальный принтер `doPDF`) слой текста для ФИО и региона отсутствует — ячейка впекается в PDF как растровое изображение.
- **Поколоночный парсинг (`parse_protocol.py`):** Извлечение текстового слоя через `pdfplumber` с привязкой к якорным колонкам времени финиша.
- **OCR растровых ячеек (`ocr_names.py`):** Обнаружение пустых текстовых блоков при наличии стартового номера $\to$ рендеринг фрагмента ячейки в 400 DPI $\to$ оптическое распознавание Tesseract 5 (языковой пакет `rus`, режим `--psm 7`).
- **Сверка со справочником СБР (`sbr_base.py`):** Распознанные строки верифицируются по связке `ФИО + Дата рождения`.
- **Точность решения (`eval_ocr.py`):** На контрольной выборке точность извлечения фамилии и имени составила **100.0%**, отчества — **98.6%**, общий посимвольный уровень ошибок (CER) — всего **0.17%**.

### 4.3 Проверки качества биатлонных протоколов

1. **Сверка с подвалом судейской коллегии:** Точное совпадение счетчиков протокола (ФИН, НС, НФ, ДСКВ, КРУГ, ВСЕГО) с числом извлеченных строк.
2. **Хронология мест:** Места строго непрерывны, начинаются с 1.
3. **Монотонность хода:** Время финишеров строго возрастает с местом.
4. **Стрелковый баланс:** Число рубежей идентично у всех участников гонки, а сумма промахов на рубежах (`Л + С + Л + С`) строго равна итоговому столбцу «Сум».

### 4.4 Запуск парсера биатлона

```bash
# Установка зависимостей (требуется Tesseract 5 в ОС с tessdata/rus.traineddata)
pip install requests beautifulsoup4 pdfplumber pillow pytesseract pydantic

# Запуск сбора Кубка России (сезон 2025/26)
python parser_biathlon/run.py --season 2025-2026 --filter kubok-rossii --max-races 40 --tag cup

# Запуск сбора Чемпионата России
python parser_biathlon/run.py --season 2025-2026 --filter chempionat-rossii --max-races 40 --tag champ

# Оценка качества OCR
python parser_biathlon/eval_ocr.py

# Сводный отчет по результатам
python parser_biathlon/summarize.py
```

## 5. Анализ расхождений: ТЗ vs Реальность данных

В ходе практического анализа реальных данных выявлены существенные расхождения между исходным ТЗ и фактами на спортивных площадках:

| Параметр из ТЗ | Предположение ТЗ | Фактическая реальность в данных | Реализованное решение |
|---|---|---|---|
| **Дата рождения** | Предполагалось, что в протоколах есть полная дата рождения (ДД.ММ.ГГГГ). | В беговых протоколах точной даты рождения **нет (0%)**. Точный год указан лишь у 2.6% (Grom). В **97.4% случаев указывается только текущий возраст (`age`)** на дату старта. | Расчет расчетного года рождения ($\text{Год старта} - \text{Возраст}$) с обязательным соревновательным допуском **$\pm 1$ год** при поиске и склейке профилей. |
| **Идентификатор атлета** | Считалось, что `participantId` на платформе RussiaRunning является сквозным ID человека. | `participantId` генерируется заново для каждого соревнования и между разными стартами никогда не повторяется. | `participantId` используется только как эталон для склейки зеркал одного старта; сопоставление атлетов между стартами переведено на алгоритм взвешенного матчинга. |
| **Поиск сотрудников по клубу** | Использовать жесткую подстроку `Sber\|Сбер\|СБТ\|STT`. | Наивный поиск по подстроке дает ложные срабатывания: клуб «Айсберг», «Shelestteam», «JusTTri». При этом аббревиатура «СБТ» в реальных протоколах не встретилась ни разу. | Поиск по подстроке `сбер/sber`, поиск по коротким аббревиатурам `СТТ/STT` **строго по границам слов**, стоп-лист исключений («Айсберг»). |
| **Скрытые клубы** | Клуб всегда виден в строке протокола. | На RussiaRunning в 10% случаев участник привязан к клубу Сбера в системе, но в печатном протоколе поле скрыто организатором. | Реализован обход участников через фильтр `clubCode` API RussiaRunning, что вернуло в выборку 22 потерянных сотрудника. |
| **Наличие клуба на площадках** | Клуб есть на всех беговых сайтах. | В протоколах **results.runc.run поле клуба отсутствует полностью (0%)**, несмотря на то, что там проходит титульный «СберПрайм Московский Марафон». | Предусмотрен механизм поиска сотрудников на runc по совпадению ФИО и года рождения с базой ранее идентифицированных атлетов, а также ручной импорт списков участников от Сбера. |
| **Монотонность времени финиша** | Места в беге всегда выстроены по возрастанию времени. | Порядок мест зависит от регламента дистанции: в части гонок места присуждаются по **чистому времени** (по коврику), в части — по **пистолетному** (от общего выстрела). В стадионных спринтах действуют правила финалов. | Автоматическое определение правила ранжирования для каждой конкретной дистанции (`race.place_by`) и маркировка стадионных финалов как известных исключений. |
| **Чиповое время на трейлах** | Всегда доступно чистое время. | На трейлах и кроссах стартовый коврик часто отсутствует, доступно только общее время. | Использование доступного пистолетного времени для расчета баллов без дисквалификации дистанции. |
| **Биатлонные правила** | Фиксированная цена штрафа (1 минута). | В коротких индивидуальных гонках на 15 км цена промаха составляет **45 секунд**, а очки в протоколе могут делиться пополам (`56,5 / -`) при параллельном зачете между двумя регионами. | Динамическое чтение регламента дистанции и парсинг составных очков. |

## 7. ИИ-агенты платформы

### 7.1 Агент персональной оценки спортсмена

В соответствии с указаниями куратора, система строго разделяет математику и языковую модель:
1. **Детерминированный слой (`analytics_service.py`):**
   - **Соревновательный процентиль:**  
     $$\text{Percentile} = \frac{N_{\text{участников}} - \text{Place} + 1}{N_{\text{участников}}} \times 100\%$$
   - **Относительный прогресс PB:** процент изменения темпа между первым и лучшим забегом на каждой дистанции.
   - **Коэффициент вариации темпа (стабильность):**  
     $$CV = \frac{\sigma}{\mu} \times 100\%$$
2. **Генеративный слой (`agent_service.py`):**  
   Компактный JSON с числовыми фактами передается в языковую модель **GigaChat API**. Модель формирует структурированное персональное резюме: сильные стороны, динамика, рекомендации по целевым стартам.
3. **Локальный движок (Fallback):**  
   При отсутствии API-ключа GigaChat приложение автоматически генерирует аналогичный аналитический отчет силами локального экспертного модуля, не прерывая работу пользователя.
4. **Кэширование:**  
   Сгенерированный отчет кэшируется в таблице `athlete_assessment_cache`. Повторные открытия профиля не расходуют токены и отображаются мгновенно.

### 7.2 Заготовка MCP Fallback-агента самовосстановления

Для решения проблемы неожиданной смены разметки на сайтах соревнований спроектирован контур агента на базе Model Context Protocol (MCP):
- **Валидатор (`app/mcp_agent/validator.py`):** Отслеживает аномалии в собранных данных (доля `NULL` в ФИО/времени $>5\%$, нарушение монотонности мест).
- **Инцидент-менеджер (`app/mcp_agent/orchestrator.py`):** При обнаружении деградации парсера регистрирует инцидент в таблице `issue` со статусом `agent_working`.
- **Инструменты MCP (`app/mcp_agent/mcp_client.py`):** Агент получает контекст инцидента и вызывает инструменты:
  - `playwright_fetch_page` — открытие страницы в реальном браузере и получение DOM/скриншота;
  - `llm_extract_table` — извлечение таблицы результатов с помощью LLM по заданной JSON-схеме;
- Извлеченные данные передаются администратору на валидацию перед записью в рейтинг.

## 8. Методика расчета баллов и рейтингов

Все расчетные модули спроектированы как чистые функции `(результат, контекст) -> (баллы, расшифровка)` и покрываются эталонными тестами (Golden Tests).

### 8.1 Бег (шоссе и стадион)
Баллы начисляются относительно официальных нормативов заказчика на 2026 год:
$$\text{Баллы} = \frac{\text{Норматив (сек)}}{\text{Время атлета (сек)}} \times 1000$$
- Зачетные дистанции: 60м, 100м, 200м, 400м, 800м, 1000м, 1500м, 1 миля, 3000м, 5000м, 10000м (стадион и шоссе), полумарафон (21.1 км), марафон (42.2 км), 100 км.
- Суточный бег (24 ч): $\frac{\text{Дистанция атлета (км)}}{\text{Норматив (км)}} \times 1000$.

### 8.2 Лыжные гонки и биатлон
Итоговый лыжный рейтинг складывается из очков за гонки и сезонных очков серии марафонов Russialoppet (RL):
$$\text{Рейтинг} = \sum \text{Баллы гонок} + (\text{Очки RL за сезон} \times K_{RL})$$
*(где $K_{RL} = 1/7$ по умолчанию).*

- **Баллы за отдельную гонку (включая биатлон):**  
  $$\text{Баллы} = 100 \times \frac{N_{\text{финишеров пола}} - \text{Место в поле} + 1}{N_{\text{финишеров пола}}}$$
- **Очки Russialoppet:** рассчитываются по официальной формуле кубка RL:  
  $$R = \left(2 - \frac{T_{\text{атлета}}}{T_{\text{лидера группы}}}\right) \times 1000$$
  *(Марафоны серии RL не учитываются в формуле места, чтобы исключить двойной счет одного старта).*

### 8.3 Триатлон
Адаптированная методика TriStats:
$$\text{Баллы} = \max\left(0, \left(R_{max} \times \left(1 - \frac{T_{\text{атлета}} - T_{\text{лидера}}}{T_{\text{лидера}}}\right) + B_{med}\right) \times K\right)$$
- $R_{max}$: Полная дистанция — 10 000; Половинка (113) — 5 000; Олимпийка — 2 500; Спринт — 1 250; Суперспринт/Индор — 625.
- Бонус за опережение медианы: $B_{med} = 2 \times \max(0, T_{\text{медиана}} - T_{\text{атлета}})$ (в минутах). Если атлет медленнее медианы группы — $B_{med} = 0$.
- Коэффициент статуса старта $K$: $1.0$ (стандартный); $1.10$ (Чемпионат мира); $1.15$ (Kona).

### 8.4 Трейл
$$\text{Баллы} = 10 \times \left(\text{Дистанция (км)} + \frac{\text{Набор высоты } D+ \text{ (м)}}{100}\right) \times \left(1 - \frac{T_{\text{атлета}} - T_{\text{лидера}}}{T_{\text{лидера}}}\right)$$
*(При отсутствии подтвержденного набора высоты $D+$ старт классифицируется как незачетный до модерации).*

### 8.5 Агрегация рейтинга
- По умолчанию включен режим **`sum_all`** (сумма баллов за все старты сотрудника за скользящие 365 дней).
- При равенстве баллов выше располагается атлет с более высоким баллом за одиночный лучший старт.

## 9. Руководство по установке и запуску

### 9.1 Системные требования
- **ОС:** Linux, macOS, Windows (PowerShell / WSL).
- **Python:** 3.12 или 3.14.
- **Docker & Docker Compose** (для промышленной СУБД PostgreSQL).
- **Tesseract OCR 5** (только для модуля распознавания биатлона).

### 9.2 Быстрый старт демонстрационного веб-приложения (SQLite)

```bash
# 1. Клонирование репозитория и переход в каталог
git clone https://github.com/czczczt/sports-agent.git
cd sports-agent

# 2. Создание и активация виртуального окружения
python -m venv .venv
# Для Windows:
.venv\Scripts\activate
# Для Linux/macOS:
source .venv/bin/activate

# 3. Установка зависимостей
pip install -r requirements.txt

# 4. Настройка конфигурации .env
cp .env.example .env
# При необходимости укажите ключ GIGACHAT_CREDENTIALS в .env

# 5. Первоначальная индексация спортсменов (выполняется ~4 сек для 297 тыс. записей)
python init_athletes.py

# 6. Запуск веб-сервера
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

После старта доступны интерфейсы:
- 🌐 **Веб-интерфейс рейтингов и аналитики:** [http://localhost:8000/](http://localhost:8000/)
- 📄 **Интерактивная документация REST API (Swagger):** [http://localhost:8000/docs](http://localhost:8000/docs)

# Тестирование логики поиска, фильтрации, UI, API и аналитики (7 тестов)

- Внедрение Golden Tests по эталонным таблицам организаторов для контроля точности формул при любых обновлениях кодовой базы.
