## 1. Архитектура и стек технологий

### 1.1 Сквозной конвейер данных

```text
[Источники] ──> [Сбор / JSON-рецепт] ──> [Raw-кэш] ──> [6 инвариантов] ──> [Сбер-фильтр и ПДн] ──> [Рейтинг] ──> [UI / API]
                       ▲                                        │
                       └──── [LangGraph + GigaChat-2-Pro] <─────┘ (при сбое вёрстки или времени)
```

1. **Реестр источников и сбор:** прямые HTTP/JSON API коннекторы (`russiarunning`, `timerman`, `runc`, `grom` и др.) и декларативные CSS-рецепты (`Crawl4AI JsonCssExtractionStrategy` + `BeautifulSoup4` / `lxml`).
2. **Raw-слой:** сохранение исходных HTML/JSON-снимков с хэшем SHA-256 (`raw`) для воспроизводимой проверки эталонов (`golden_case`) и повторного сбора.
3. **Самовосстановление без кода (`app/recipe_agent`):** при поломке вёрстки или колонки времени создаётся инцидент в `issue`, граф на `LangGraph` запрашивает новый JSON-рецепт у `GigaChat-2-Pro`, проверяет его на эталонах и ставит задачу на паузу в `/agent-review`.
4. **Валидация и нормализация:** аудит протокола по 6 математическим инвариантам, нормализация времён, дистанций, ФИО и определение принадлежности к клубам Сбера (`is_sber_club`).
5. **Контур ПДн и обезличивания:** посторонние участники (`not_employee`) скрываются из поиска и рейтинга, а их строки в протоколах обезличиваются как `Участник`.
6. **Рейтинговый движок и веб-платформа:** расчёт баллов за 365 дней (`run-v1`), личные профили, модерация заявок и очередь проверки сотрудников.

### 1.2 Актуальный стек технологий

* **Бэкенд:** Python 3.12 / 3.14, FastAPI, Starlette, Uvicorn, Pydantic v2, `pydantic-settings`.
* **База данных и миграции:** PostgreSQL 16/18, `SQLAlchemy[asyncio]`, `asyncpg`, `psycopg[binary,pool]` (v3), Alembic.
* **Фоновые очереди:** Procrastinate (очереди задач в PostgreSQL без Redis).
* **Безопасность:** `argon2-cffi` (хэширование паролей), HMAC-подписанные токены, таблица отозванных токенов (`revoked_token`).
* **Фронтенд (`frontend/`):** React 18, TypeScript, Vite 5, React Router 7, TanStack Query, Chart.js, Air Datepicker, OpenAPI-типизация (`frontend/dist` отдаётся напрямую через FastAPI).
* **ИИ-агент и парсинг:** `LangGraph`, `langgraph-checkpoint-postgres`, `langchain-gigachat`, `gigachat`, `langchain-core`, `crawl4ai`, `beautifulsoup4`, `lxml`, `pdfplumber`, `pypdfium2`, `openpyxl`, `httpx`, `requests`, `regex`.

## 3. Авторизация, роли и защита ПДн

Сервис работает в **закрытом корпоративном контуре**: все доменные маршруты API (`/api/...`, кроме `/api/auth/*` и `/health/*`) требуют авторизации.

### 3.1 Роли в системе
* **`user` (сотрудник):** поиск, просмотр рейтинга, каталога стартов, протоколов, своего профиля и подача обращений/заявки на привязку профиля («Это я»).
* **`captain` (капитан вида спорта):** права `user` + модерация заявок/обращений и очереди проверки сотрудников (`verify-queue`), просмотр ПДн спортсменов.
* **`admin` (администратор):** полный доступ ко всем разделам, включая массовый сбор, мониторинг `/status`, управление пользователями и подтверждение ИИ-рецептов в `/agent-review`.

### 3.2 Матрица видимости ПДн и Сбер-контур
1. **В протоколах дистанций (`/races-view/{id}`):**
   * Участники не из Сбера (`not_employee`) **для всех ролей** обезличены: имя отображается как `Участник`, скрыты `athlete_id`, нагрудный номер (`bib`), клуб, город и рейтинг.
   * Сотрудники Сбера (`presumed` / `confirmed`, клубы `ПАО Сбербанк`, `Sberbank Triathlon Team`, `SBERRUN`, `SBER Team`, `STT`, `Сбер` и др., кроме стоп-слов вроде `Айсберг`) отображаются с именем, номером, клубом и ссылкой на профиль.
2. **В поиске и карточке спортсмена (`/athletes/search`, `/athletes-view/{id}`):**
   * Участники со статусом `not_employee` скрыты из поиска и не открываются обычным пользователям (`404`).
   * **Обычный пользователь (`user`):** видит только `display_name`, `birth_year`, `gender`, старты и рейтинг; поля **`middle_name` (отчество), `birth_date` (точная дата рождения), `city`, `region`, `club` обнуляются**.
   * **Капитан, администратор и владелец профиля (`athlete_id == user.athlete_id`):** видят полные ПДн (включая отчество, дату рождения, город, регион и клуб).

## 4. Сбор данных и контроль качества (`parser_running`, `app/pipeline`)

Поддерживаемые источники в таблице `source`: `russiarunning`, `timerman`, `runc`, `grom`, `ironstar`, `legkovrace`, `myfinish`, `myrunstats`, `orgeo`, `pionercup`, `probeg`, `racetime`, `resultszone`, `russialoppet`, `toplist`, `tristats`.

### 6 инвариантов валидации протокола
Перед сохранением протокола в БД проверяются инварианты (`parser_running/store.py`, `app/recipe_agent/extraction.py`):
1. **Полнота выборки** — число финишировавших совпадает с заявленным организатором.
2. **Определённость пола** — валидный пол (`M` / `F`), отсев пустых записей.
3. **Наличие результата** — у всех со статусом `FIN` есть время финиша.
4. **Непрерывность мест** — порядок мест от `1` без пропусков.
5. **Монотонность времени** — время по шкале сортировки (`chip` или `gun`) не убывает с ростом места.
6. **Контроль статусов** — допустимые статусы: `FIN`, `DNF`, `DNS`, `DSQ`, `NC`, `LAP`.

## 6. ИИ-агент восстановления рецептов (`app/recipe_agent`) и аналитика

### 6.1 Цикл самовосстановления JSON-рецептов
Контур реализован без модификации Python-кода адаптеров на базе `LangGraph` + `AsyncPostgresSaver` (`app/recipe_agent/graph.py`, `collection.py`, `provider.py`):

1. **Детект сбоя вёрстки и времени:** при попытке сбора старый рецепт падает на `InvalidProtocol` (например, изменился CSS-селектор таблицы или класс времени `gun`), фиксируется инцидент `recipe_regression` в `issue` и стартует `recipe_repair`.
2. **Генерация JSON-рецепта без кода:** агент передаёт компактный HTML в `GigaChat-2-Pro` (`GIGACHAT_VERIFY_SSL=false`) и получает новый JSON-рецепт (`baseSelector` + поля извлечения) с пробным прогоном (`Crawl4AI JsonCssExtractionStrategy`).
3. **Проверка на эталонах (`golden_case`):** кандидат сверяется с сохранёнными эталонными протоколами (`3 из 3`).
4. **Пауза на ревью в «Правках агента» (`/agent-review`):** при `AUTO_APPLY_SAFE_REPAIRS=false` граф останавливается в статусе `waiting`. В карточке доступны:
   * **«Активировать рецепт»** (`approve`) — выпуск новой версии рецепта;
   * **«Перепроверить JSON»** (`edit`) — повторный прогон отредактированного/текущего JSON на проблемном протоколе и эталонах с возвратом в `waiting` без автоактивации;
   * **«Отклонить»** (`reject`).
   После нажатия карточка остаётся закреплённой на экране с выводом результата обработки.
5. **Повторный сбор:** после активации новой версии `recipe_version` автоматически запускается сбор упавшего забега с сохранением результатов в `result` (`saved_rows`).

### 6.2 Персональная оценка спортсмена
Детерминированные метрики (`app/services/analytics_service.py`: процентиль, динамика PB, $CV$ темпа) с кэшированием отчёта в `athlete_assessment_cache`.

## 7. Рейтинговый движок и расчёт баллов

Расчёт баллов (`app/modules/rating/`, `parser_running/scoring.py`) детерминирован и опирается на нормативы 2026 года:

$$\text{Баллы} = \frac{\text{Норматив (сек)}}{\text{Время атлета (сек)}} \times 1000$$

* Зачётные дистанции: от `60m` до `marathon`, `100k` и `24h` (для суточного бега: $\frac{\text{Дистанция}}{\text{Норматив}} \times 1000$).
* Агрегация `sum_all` за скользящие 365 дней; тай-брейки: лучший старт (`best_points`) → число стартов (`starts_count`) → `athlete_id`.
* Для расчётных рейтингов исключаются скрытые профили (`is_hidden = TRUE`) и посторонние (`employee_status = 'not_employee'`).

## 8. Запуск, перенос БД и тестирование демо

### 8.1 Подробное развёртывание и перенос БД
Полная пошаговая инструкция по установке PostgreSQL с нуля, импорту готового дампа **`sports_agent_dump.dump`**, настройке `.env`, сборке фронтенда и запуску на новом компьютере вынесена в отдельный файл:
👉 **[DEPLOY_GUIDE.md](DEPLOY_GUIDE.md)**

Краткий список шагов для Windows (PowerShell):
1. Установить PostgreSQL (`5432`), создать пользователя `agent` (пароль `change-me`) и базу `sports_agent`.
2. Создать виртуальное окружение и поставить зависимости: `pip install -r requirements.txt`.
3. Восстановить базу из дампа:
   ```powershell
   $env:PGPASSWORD="change-me"
   pg_restore -h 127.0.0.1 -p 5432 -U agent -d sports_agent --clean --if-exists --no-owner "sports_agent_dump.dump"
   ```
4. Создать `.env` в корне проекта:
   ```env
   RUNNING_DB_PATH=running.db
   DATABASE_URL=postgresql://agent:change-me@127.0.0.1:5432/sports_agent
   DEFAULT_AUTHOR=cz
   GIGACHAT_CREDENTIALS=<ключ>
   GIGACHAT_MODEL=GigaChat-2-Pro
   GIGACHAT_VERIFY_SSL=false
   AUTO_APPLY_SAFE_REPAIRS=false
   ```
5. При необходимости собрать фронтенд: `cd frontend && npm.cmd install && npm.cmd run build && cd ..`.
6. Запустить сервер (флаг `--loop` обязателен на Windows для асинхронного `psycopg`):
   ```powershell
   python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --loop app.core.database:postgres_event_loop_factory
   ```

Учётные записи в демо-базе: `admin` / `admin`, `captain` / `captain`, `user` / `user`.

### 8.2 Демонстрация ИИ-агента одной командой (`test_agent.py`)
Для сквозной демонстрации ремонта без запуска отдельного воркера:
```powershell
python test_agent.py
```
Скрипт проверяет подключение к `GigaChat`, запускает два сценария поломки (`вёрстка` и `время`), выводит в консоль ошибки парсинга, генерирует через GigaChat новые JSON-рецепты, прогоняет эталоны (`3/3`), ставит задачи на паузу и ждёт подтверждения администратора на `http://127.0.0.1:8000/agent-review` — после клика **«Активировать рецепт»** скрипт дособирает результаты в БД.
