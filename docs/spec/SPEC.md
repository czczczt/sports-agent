## 1. Цель и границы

Платформа собирает результаты сотрудников Сбера на любительских стартах по бегу, лыжам (включая биатлон), триатлону и трейлу. По этим результатам она считает баллы по утверждённым формулам и показывает рейтинги, карточки спортсменов и карточки стартов. Сейчас эта работа делается вручную в Excel и Google-таблицах.

**Входит в MVP**
- Доступ только после входа: регистрация по email и паролю, ручная модерация заявок, блокировка при снятии статуса «сотрудник».
- Автоматический сбор результатов со **всех** источников из списка заказчика (§6). Порядок подключения определяет ценность источника, а не объём MVP.
- Ручная загрузка протоколов (Excel/CSV) с сопоставлением колонок. Через неё же грузятся внутренние старты Сбера: чемпионат ЦА, Сбербанкиада.
- Спортсмены: ручное создание, импорт списков, детектор клуба, нечёткое сопоставление, очередь модерации, статус сотрудника.
- Баллы по бегу, лыжам (+ биатлон, очки RL) и триатлону. Трейл — последним этапом MVP.
- Рейтинг за скользящие 365 дней, срез на дату, архив годов и сезонов.
- Экраны для пользователя:
  - рейтинги;
  - карточка спортсмена с разбором баллов и динамикой места;
  - карточка старта;
  - календарь стартов: прошедшие, запланированные, число сотрудников в прошлом выпуске;
  - связка учётки со спортсменом («это вы»);
  - заявка об ошибке, «добавьте мой старт», «скрыть меня»;
  - карточка для соцсетей.
- Роль «капитан»: администратор данных своего вида спорта.
- Админка: пользователи и заявки на доступ, модерация, спортсмены, старты и календарь, загрузка, источники, настройки.

**Не входит в MVP**
- Личный кабинет сотрудника: вход нужен только для просмотра и заявок. Потребность «довнести свой старт» закрывает заявка.
- Подразделения: поле, справочник, фильтр и показ удалены полностью (решение v1.3, ⏳ Мария).
- Интеграция с «Пульсом» и с реестром сотрудников. Сверка в «Пульсе» — ручная, вне системы; система хранит только факт, кто и когда проверил.
- Вход через Telegram. Telegram остаётся только для алертов админу.
- Бюджет и квоты слотов в календаре: показываем числа, расчёта нет.
- Возрастные коэффициенты в беге (таблицы WMA) — бэклог.
- ИИ-ассистент для зрителей — бэклог.
- Сценарии «организатор старта ищет спортсменов» из экранов студентов.
- PDF и сканы без текстового слоя.

**Масштаб:** десятки пользователей, сотни спортсменов, тысячи результатов в год. Одна VM, нагрузка не проектируется.

## 2. Роли

Единый вход для всех ролей. Без входа доступны только экраны входа, регистрации и сброса пароля.

| Роль | Кто | Что может |
|---|---|---|
| Пользователь | сотрудник, зарегистрировался и прошёл модерацию (`status = active`) | смотреть рейтинги, карточки спортсменов и стартов, календарь (только числа); связать учётку со спортсменом; отправить заявку: «это не мой результат», «добавьте мой старт», «скрыть меня», «ошибка в данных» |
| Капитан | капитаны сборных и актив сообществ; роль выдаёт админ, привязана к видам спорта | всё, что пользователь, плюс полная ДР и отчество; администрирование данных своего вида спорта (ниже) |
| Администратор | 1–5 ответственных за рейтинг | всё, включая то, что капитану запрещено |

**Капитан** — администратор данных. Может:
- модерировать совпадения и разбирать заявки (в том числе «скрыть меня»);
- править карточки спортсменов, статус сотрудника (`employee_status`), `is_hidden`;
- объединять дубли и отвязывать ошибочные результаты;
- грузить протоколы вручную;
- править старты: класс дистанции, вид спорта и дисциплину, D+, отметку «марафон серии RL», статус ЧМ / Кона;
- вести календарь: добавлять запланированные старты, склеивать их с сериями;
- одобрять и отклонять заявки на доступ (любые, без привязки к виду спорта);
- выгружать рейтинг и карточки в Excel.

Капитану **запрещены**: настройки, источники, пользователи и роли, удаление протоколов.

**Скоуп капитана:** правки — только по его видам спорта (`CaptainSport`), просмотр — по всем. Спортсмен относится к виду спорта капитана, если у него есть результаты в этом виде ⏳. Все действия пишутся в `AuditLog`. Смена статуса на `not_employee` дополнительно попадает в сводку администратору.

**Видимость персональных данных**

| Поле | Пользователь | Капитан, админ |
|---|---|---|
| Фамилия, Имя, год рождения | да | да |
| Отчество, полная дата рождения | нет | да |
| Город, клуб из протокола | нет (в карточке не показываются) | да, в админских экранах |
| Список сотрудников на старте | да (только сотрудники, без посторонних) | да |
| Календарь | только числа | только числа |

Страницы закрыты от поисковиков (`noindex` и `robots.txt`) — это дополнительная защита, а не механизм доступа.

## 3. Сценарии

### 3.1 Вход и доступ
- **Регистрация.** Поля: email, пароль, Фамилия, Имя, Отчество, дата рождения, город, чекбокс согласия на обработку ПДн со ссылкой на политику. Создаётся учётка со статусом `pending`, пользователь видит экран «Заявка на рассмотрении».
- **Вход.** Email и пароль. Статус `pending` — экран ожидания; `blocked` и `rejected` — экран «Доступ закрыт». После N неудачных попыток вход блокируется на время (§12).
- **Сброс пароля.** Пользователь запрашивает ссылку на email; администратор может инициировать сброс из карточки пользователя.
- **Заявки на доступ.** Админ или капитан видит очередь заявок: данные регистрации рядом с предполагаемым спортсменом (кандидат по Фамилии, Имени и ДР). Решения:
  - одобрить и связать со спортсменом;
  - одобрить без связи;
  - отклонить.
  Сверку в «Пульсе» модератор делает вручную вне системы.
- **Блокировка.** Админ блокирует учётку вручную; учётка, связанная со спортсменом, получившим `not_employee`, блокируется автоматически.

### 3.2 Пользователь
- **Смотрит рейтинг.** Выбирает вид спорта, пол и возрастную группу. По умолчанию период «последние 365 дней», может открыть архив: календарный год, для лыж — сезон. Таблица: место, Фамилия Имя, год рождения, баллы, изменение за месяц, число стартов. Строка со своей учётки подсвечена «Это вы».
- **Связывает себя со спортсменом.** Если учётка связана, «это вы» подставляется автоматически, а карточка открывается из шапки. Если нет — пользователь отправляет заявку «связать меня со спортсменом» (тип `link_me` в §8.4), модератор подтверждает.
- **Открывает карточку спортсмена.** Видит:
  - Фамилию, Имя, год рождения и фото;
  - место по видам спорта и график места по месяцам;
  - результаты за период с баллами и разбором «как посчитано»;
  - для лыж отдельной строкой «Очки Russialoppet ÷ 7».
- **Сообщает об ошибке.** Форма доступна только после входа, поля «контакт» нет — связь через учётку. Типы (§8.4):
  - «это не мой результат»;
  - «я сотрудник, добавьте мой старт» (ссылка на протокол);
  - «я выступал за другой клуб, вот мои старты»;
  - «скрыть меня»;
  - «ошибка в данных».
- **Делится результатом.** Скачивает картинку «N-е место в рейтинге Сбера» (только Фамилия и Имя).
- **Открывает карточку старта.** Видит дату, город, дистанции, число финишёров, сотрудников с результатами и баллами, ссылку на первоисточник. Посторонних участников и топ-3 нет.
- **Смотрит календарь** (§3.4).

### 3.3 Капитан
- **Отбор на старт.** Фильтрует рейтинг по виду спорта, полу и группе, видит полные ДР (различает полных тёзок, подписано «тёзка»), выгружает список в Excel.
- **Срез на дату.** Рейтинг на выбранную дату, например на дату отбора.
- **Администрирование данных своего вида спорта.** Модерация, заявки, карточки спортсменов, `employee_status`, дубли и отвязка, ручная загрузка, правка стартов, календарь, одобрение доступа (полный перечень — в §2).
- **Очередь «не проверен».** Видит ту же очередь, что админ, в рамках своих видов спорта.

### 3.4 Календарь
- **Смотрит календарь.** Любой вошедший пользователь видит по месяцам прошедшие и запланированные старты. У каждого: дата, город, вид спорта, плашка «запланирован», число сотрудников в прошлом выпуске серии и их распределение по дистанциям. Только числа, списка людей нет.
- **Добавляет запланированный старт.** Капитан (по своему виду спорта) или админ указывает название, город, вид спорта, ориентировочные даты, дистанции.
- **Склейка с серией.** Система предлагает серию по названию и городу (`EventSeries`); капитан или админ подтверждает. Когда появляется фактический протокол, механизм «возможный дубль» предлагает склеить его с запланированным стартом.

### 3.5 Администратор
- **Ежедневная проверка.** Сводка в Telegram и главная админки:
  - что собрано;
  - какие адаптеры упали;
  - очередь модерации, заявок и заявок на доступ;
  - очередь «не проверен»;
  - переводы в `not_employee`, сделанные капитанами;
  - трейлы без набора высоты.
- **Очередь «не проверен».** Спортсмены в топ-N каждого рейтинга (вид × пол; `top_n_verify`, по умолчанию 10) без `employee_status = confirmed`. Из рейтинга их не убираем, очередь нужна для проверки в «Пульсе».
- **Модерация.** Кандидат из протокола рядом с предполагаемым спортсменом, процент совпадения и разбивка по полям. Решение: «это он», «новый спортсмен» или «не наш».
- **Пользователи.** Заявки на доступ, роли и виды спорта капитанов, блокировка, сброс пароля.
- **Спортсмены.**
  - Создаёт карточку вручную или импортирует список (§8.5). После создания система ищет старты спортсмена по ФИО во всех источниках с поиском.
  - Правит Фамилию, Имя, Отчество, ДР, фото.
  - Объединяет дубли, отвязывает ошибочные результаты.
  - Меняет `employee_status` и `is_hidden`.
- **Заявки.** Отвязывает результат, запускает загрузку по ссылке, привязывает старты под чужим клубом, скрывает спортсмена или отклоняет заявку.
- **Ручная загрузка.**
  1. Загружает Excel/CSV.
  2. Выбирает или создаёт старт и дистанцию.
  3. Сопоставляет колонки.
  4. Смотрит превью и импортирует.
  Так грузятся внутренние старты Сбера и протоколы с сайтов без адаптера.
- **Правка старта.**
  - Объединяет дубли.
  - Ставит статус: обычный, чемпионат мира, Кона (без числовых коэффициентов).
  - Назначает класс дистанции, вид спорта или дисциплину (бег/трейл, лыжи/биатлон), набор высоты.
  - Ставит отметку «марафон серии RL».
- **Настройки.**
  - паттерны и стоп-лист клубов;
  - нормативы и синонимы дистанций;
  - пороги сопоставления;
  - агрегация, период рейтинга, возрастные группы;
  - `top_n_verify`, TTL сырых ответов;
  - пользователи, роли и виды спорта капитанов.

Решения в модели:
- **Подразделение удалено.** Нет `Division`, `division_id`, колонки в импорте, фильтра и настройки.
- **Заявка на доступ — это `User` со `status = pending`.** Отдельной таблицы нет: регистрация и есть заявка, данные те же, жизненный цикл совпадает со статусами `pending → active | rejected`. Кандидат-спортсмен вычисляется на лету по ФИО и ДР, при одобрении фиксируется в `User.athlete_id`. Кто и когда решил — `approved_by`, `approved_at`, остальное — `AuditLog`.
- **Учётка ↔ спортсмен.** `User.athlete_id` необязателен. Одна учётка — один спортсмен, один спортсмен — не более одной активной учётки.
- **Статус сотрудника** (`Athlete.employee_status`):
  - `presumed` — ставится автоматически: детектор клуба нашёл спортсмена с сберовским клубом, либо одобрена регистрация. Входит в рейтинг;
  - `confirmed` — капитан или админ проверил в «Пульсе» вручную. Система хранит только факт, кого и когда (`confirmed_by`, `confirmed_at`);
  - `not_employee` — исключён из рейтинга, связанная учётка блокируется.
- **Снятие статуса.** Перевод в `not_employee` ставит `employee_until` (по умолчанию — сегодня). Результаты до этой даты остаются в архивных периодах, после — не учитываются.
- **Скрытый спортсмен.** `is_hidden = true` (по заявке «скрыть меня» или вручную): баллы и результаты хранятся, в выдаче его нет, места пересчитываются без него (§9.5).
- **Обезличивание.** Строка протокола несотрудника (нет `ResultLink` со статусом `auto`/`confirmed`, не `is_sber_club`) после окна сопоставления (`match_window_days`, по умолчанию 30) обезличивается: остаются пол, возрастная группа или бакет года рождения, время, место, статус; имя, клуб, номер, город, `raw` стираются, `is_anonymized = true`. Обезличенные строки нужны для лидера, медианы и числа финишёров. Дедуп и сопоставление работают до обезличивания.
- **Сырые ответы.** `FetchLog.raw` хранится `raw_ttl_days` (по умолчанию 90), затем удаляется. Нормализованные данные сотрудников остаются.
- **`ResultLink` отделён от `ResultRow`.** Привязку можно менять, не трогая сырые данные.
- **Календарь.** `Event.status = planned` для запланированных, `done` для фактических. Планируемый и фактический старт склеиваются через «возможный дубль» (§7). Число сотрудников в прошлом выпуске считается агрегатом по `EventSeries`, в том числе по скрытым спортсменам: это число, не список.
- **Статус старта.** `Event.special` — `regular` / `worlds` / `kona`; численные K живут в калькуляторе (§9.3), а не в данных старта.
- **Очки RL — отдельная таблица.** Сезонная сумма по формуле Кубка Russialoppet, а не баллы отдельной гонки. Коэффициент `1/7` — константа формулы (§9.2).
- **`Score` без периода.** Баллы за старт не зависят от периода. Период влияет только на агрегацию в `RatingEntry`. Смена констант формулы (RL ÷ 7, K) = новый `formula_version` и пересчёт.
- **Материализация.** `Score`, `RatingEntry`, `RatingSnapshot` пересчитываются, а не правятся. Окно `rolling` пересчитывается каждую ночь, архивные периоды — при изменении данных. «Срез на дату» для капитана считается запросом на лету: данных мало.
- **Объединение спортсменов** работает через `merged_into_id`.

## 6. Источники и адаптеры

Подробности по каждому сайту — в [sources.md](sources.md).

### 6.1 Интерфейс адаптера

```python
class SourceAdapter(Protocol):
    code: str
    async def discover(self, period: DateRange, club_patterns: list[str]) -> list[RaceRef]: ...
    async def fetch_protocol(self, ref: RaceRef) -> RawProtocol: ...
    def normalize(self, raw: RawProtocol) -> NormalizedProtocol: ...
    async def search_athlete(self, athlete: AthleteQuery, period: DateRange) -> list[RaceRef]: ...
```

`discover` и `search_athlete` необязательны. Если у источника нет поиска, адаптер работает только как первоисточник протоколов.

### 6.2 Три способа получения данных (`Source.fetch_mode`)

| Режим | Когда | Как |
|---|---|---|
| `http` | есть JSON API или серверный HTML | `httpx` + `selectolax`; основной режим, его ищем в первую очередь |
| `browser` | данные появляются только после JS, API не найдено | Playwright в контейнере `worker-browser`; адаптер реализует тот же интерфейс, браузер — деталь `fetch_protocol` |
| `agent` | нерегулярный источник со своей вёрсткой: статья на sports.ru, страница отдельного старта, разовые протоколы | **LLM-агент + Playwright MCP**: агент открывает страницу, находит протокол, извлекает таблицу в нормализованный CSV; файл идёт по пути ручной загрузки с проверкой админом |

Правило выбора: `http` → `browser` → `agent` → ручная загрузка.

Режим `agent` — это кейс, а не обязательная часть MVP: его подключаем, когда источников с уникальной вёрсткой станет слишком много для ручной загрузки. Для разработки и разведки Playwright MCP пригодится уже сейчас:
- смотреть сетевые запросы страницы и находить скрытый JSON API за JS-фронтендом;
- снимать фикстуры для тестов адаптеров.

Результат агента никогда не попадает в рейтинг напрямую, только через превью и подтверждение админа. Так ошибка извлечения не испортит баллы.

В MVP — **все** источники из списка заказчика. Порядок подключения — по ценности: сначала источники с поиском по клубу и основная масса стартов. Окончательная матрица — в [sources.md](sources.md) после разведки 2026-10-23.

**Лига Героев** без года рождения и клуба: сотрудников ищем только по ФИО известных спортсменов, автопривязки нет, все совпадения идут в модерацию. Бег с препятствиями (OCR) и вело в рейтинг не идут ⏳ заказчик.

**Правила работы с сайтами:**
- не больше 1–2 запросов в секунду на домен;
- понятный User-Agent;
- повтор с паузой при 5xx и таймаутах.

Если адаптер упал или вернул 0 записей там, где раньше были, в админке загорается «требует внимания» и уходит алерт в Telegram. Часть сайтов (tristats, grom) блокирует нероссийские IP, поэтому сбор работает только с российского адреса.

**Тесты адаптеров:** снимки реальных ответов (фикстуры) → `normalize` → ожидаемый `NormalizedProtocol`. Сеть в CI не используется.

## 7. Нормализация и дедуп

**Нормализация** (таблица полей — в [sources.md](sources.md#нормализация-полей)):
- **ФИО:** разбор на фамилию, имя и отчество. `name_key` = нижний регистр, `ё→е`, без дефисов и пробелов, транслитерация в кириллицу.
- **Возраст вместо ДР:** вычисляется интервал `birth_year_min..max`.
- **Пол:** явный → из группы → по словарю имён → неизвестен.
- **Время:** миллисекунды; DNF, DNS, DSQ. Если есть оба, `time_ms` — по чипу.
- **Вид спорта и дисциплина:**
  1. берутся из источника;
  2. затем ключевые слова: «трейл», «trail», «скайраннинг», «sky» → `trail`; «биатлон», стрельба «лёжа/стоя» → `biathlon`;
  3. админ или капитан может переопределить.
- **Беговой классификатор `scoring_class`:**
  1. метры с допуском ±1% для шоссе, точное совпадение для стадиона;
  2. затем матрица синонимов в названии дистанции или старта (`Setting`, правит админ):
     - «полумарафон | 21,1 | 21,195 | 21,18» → 21.1 км;
     - «марафон | 42,2 | 42,195» → 42.2 км;
     - «десятка | 10 км» → 10000;
     - «5 км | пятёрка | 5 вёрст | паркран» → 5000;
  3. иначе `null` (незачётная), админ или капитан может назначить класс вручную.
- **Триатлон** — по формату из источника или по сумме этапов.
- **Трейл** — класс `trail` для любой длины; без `elevation_gain_m` гонка незачётная.
- **Марафоны серии RL** — по списку стартов серии с russialoppet.ru ставится `Race.is_rl_series`.

**Дедуп:**
- **Event** — та же дата (±1 день) + схожесть названий ≥ 0.85 (trigram) + тот же город, если известен.
- **Race** — тот же Event + `distance_m` ±1% + тот же вид спорта и признак эстафеты.
- **Приоритет протокола:** первоисточник важнее агрегатора.
- **ResultRow** — та же Race + `name_key` + время ±1 с (до обезличивания).
- **Запланированный старт** (`Event.status = planned`) — кандидат на склейку с фактическим `Event` той же серии (название, город, даты в пределах планового окна). Автоматически не склеивается: «возможный дубль» подтверждает капитан или админ.
- **Серия** (`EventSeries`) — подсказка по названию, городу и сезону; привязку подтверждает капитан или админ.

## 8. Поиск сотрудников

### 8.1 Детектор клуба
`ClubPattern(include)` — регистронезависимо, после транслитерации:
- **Подстрока** (`match = substring`): `сбер`, `sber`. Ловит SBERTEAM, SBERбарнаул, TeamSber, СберРядом, Сбербанк, ПАО «Сбербанк».
- **Целое слово** (`match = word`): `стт`, `stt`, `сбт`. Это короткие аббревиатуры: СТТ — триатлонная команда Сбера (Sber Triathlon Team).
- **Полный список тегов** присылает заказчик ⏳ и заносит админ.

`ClubPattern(exclude)` — стоп-лист. Подстрока «сбер» ловит «айсберг», «Айсберг-Ран» и подобные, их исключаем.

Спортсмен, найденный по клубу, получает `employee_status = presumed`.

**Отчёт для админа:** все уникальные названия клубов, которые сработали, с числом строк. Ложное срабатывание видно сразу и добавляется в стоп-лист одним кликом.

После правки паттернов детектор перезапускается по всем необезличенным строкам.

### 8.2 Сопоставление строки со спортсменом

**Кандидаты:** `pg_trgm`-поиск по `name_key` среди `Athlete` и `AthleteAlias` с учётом перестановки имени и фамилии, топ-5.

**Оценка** (0..1) — взвешенная сумма по полям, которые есть с обеих сторон. Веса перенормируются.

| Поле | Вес | Как сравнивается |
|---|---|---|
| Фамилия | 0.40 | rapidfuzz ratio по кириллице после транслита |
| Имя | 0.25 | то же; словарь уменьшительных — после MVP |
| Отчество | 0.05 | если есть с обеих сторон |
| Дата / год рождения | 0.20 | дата = 1; год = 1; год в интервале по возрасту = 0.8; разница в год = 0.5 |
| Город | 0.05 | точное совпадение |
| Клуб «Сбер» в строке | 0.05 | бонус |

**Жёсткие отказы:** разный известный пол; разница годов рождения больше 1.

| Оценка | Действие |
|---|---|
| ≥ 0.90 | автопривязка (`auto`) |
| 0.75–0.90 | модерация (`pending`) |
| < 0.75 | игнор |

Если кандидатов нет, а клуб сберовский, создаётся предложение «новый спортсмен» в модерации. Пороги — в настройках (ТЗ: 80–90%).

**Расхождение с драфтом:** на экране модерации в драфте V2 (стр. 41–44) порог автопривязки подписан 95%, в спеке 0.90. По умолчанию берём **0.90** (в пределах 80–90% ТЗ); значение — настройка, для выравнивания драфта и спеки нужно решение ⏳ заказчик.

**Полные тёзки.** Если по ФИО подходят два спортсмена, а ДР в протоколе нет, автопривязки не бывает: строка всегда уходит в модерацию. Фактических полных тёзок с одной ДР в одном виде спорта заказчик не ожидает; метка «тёзка» на экране капитана остаётся как страховка.

### 8.3 Модерация
Карточка в очереди: строка протокола (все поля + ссылка на источник) и кандидаты с разбивкой оценки. Доступна админу и капитану (капитану — по своим видам спорта).

Действия:
- **подтвердить** — ФИО строки добавляется в `AthleteAlias`;
- **другой спортсмен**;
- **новый спортсмен**;
- **отклонить**.

Есть групповые действия.

### 8.4 Заявки пользователей
Форма доступна только после входа. Поля:
- тип заявки;
- текст;
- ссылка на протокол.

Поля «контакт» нет: ответ идёт через учётку и email. Защита: ограничение частоты по пользователю. Разбирают заявки админ и капитан во вкладке модерации.

| Тип | Что происходит |
|---|---|
| `not_me` — «это не мой результат» | отвязка результата |
| `add_start` — «добавьте мой старт» | загрузка по ссылке на протокол |
| `other_club` — «я выступал за другой клуб» | привязка стартов под чужим клубом; дальше их подхватывает правило «один раз за Сбер — все результаты в зачёт». Закрывает случай капитана бега: на части стартов он пишет клуб тренера (G-Sports) |
| `hide_me` — «скрыть меня» | модератор ставит `is_hidden`: спортсмен считается, но не показывается (§9.5). Правовое основание публикации ⏳ юристы заказчика (§13) |
| `link_me` — «связать меня со спортсменом» | модератор подтверждает `User.athlete_id` |
| `data_error` — «ошибка в данных» | правка карточки или старта |

### 8.5 Ручное создание и импорт спортсменов
- **Форма.** Фамилия, Имя, Отчество, ДР или год, пол, город, виды спорта, фото, `employee_status`.
- **Импорт CSV/XLSX.** Колонки сопоставляются так же, как в загрузке протоколов.
  - Совпадение с существующим спортсменом определяется тем же сопоставлением (§8.2). Совпавшие обновляются, новые создаются.
  - В отчёте видно, сколько строк создано, сколько совпало и где ошибки.
- **Первые списки:** зарегистрированные за СТТ (есть у капитана триатлона) и лист «Участники» лыжного Excel (ФИО, пол). Колонка подразделения не импортируется.
- **Поиск стартов.** После создания запускается шаг [7]: поиск стартов по ФИО во всех источниках с поиском. Найденные строки проходят обычное сопоставление.

### 8.6 Заявки на доступ
Регистрация (§3.1) создаёт `User` со `status = pending`. В очереди модератор видит данные регистрации и кандидата-спортсмена, подобранного по Фамилии, Имени и ДР (кандидатов может не быть). Решения:
- **одобрить со связью** — `status = active`, `athlete_id` заполнен; если спортсмена нет, создаётся с `employee_status = presumed`;
- **одобрить без связи** — `status = active`, `athlete_id = null`;
- **отклонить** — `status = rejected`.

Сверку в «Пульсе» модератор делает вручную до решения. Одобрение — действие в `AuditLog`.

### 8.7 Статус сотрудника
| Статус | Как ставится | В рейтинге | Доступ |
|---|---|---|---|
| `presumed` | автоматически: детектор клуба или одобренная регистрация | да | да |
| `confirmed` | капитан или админ после ручной проверки в «Пульсе» (фиксируются кто и когда) | да | да |
| `not_employee` | капитан или админ | нет | связанная учётка получает `blocked` автоматически |

Приоритет проверки — спортсмены в топ-N рейтинга (§3.5). Учётки без связи со спортсменом (`athlete_id = null`) автоматически не блокируются: блокирует модератор.

## 9. Баллы и рейтинг

Все калькуляторы — чистые функции: `(результат, контекст дистанции, настройки) → баллы + расшифровка`. Пересчёт запускается при любом изменении входных данных. Константы формул (RL ÷ 7, K) версионируются через `formula_version` и не вынесены в настройки.

### 9.1 Бег (шоссе и стадион)
- `баллы = норматив_сек / время_сек × 1000` по `RunNorm(год, класс, пол)`. Подпись на экране: «Нормативы по году, дистанции и полу».
- Нормативы — стадионные до 10 000 м включительно и шоссейные от 21,1 км. Так устроена текущая таблица заказчика. Забег на 10 км по шоссе считается по стадионному нормативу 10 000 м.
- Зачётные классы: 60, 100, 200, 400, 800, 1000, 1500 м, миля, 3000, 5000, 10000 м, 21.1, 42.2, 100 км, 24 ч.
- 24 ч: `км / норматив_км × 1000`.
- Нужен пол; без пола — модерация.
- Нестандартные дистанции незачётные, пока админ или капитан не назначит класс. Предложение «время победителя = 1000» не берём: у него другая шкала, и слабый по составу забег давал бы больше баллов, чем сильный.

### 9.2 Лыжи (лыжные гонки + биатлон + марафоны RL)
Итог лыжного рейтинга за период:

```
лыжи = Σ баллы_гонок (лыжные гонки и биатлон, кроме марафонов серии RL)
     + очки_RL_за_сезон ÷ 7
```

`1/7` — константа формулы (версионируется через `formula_version`), в настройках её нет.

- **Гонка:** `баллы = 100 × (N − место + 1) / N`.
  - N — финишёры того же пола на этой дистанции, место — среди того же пола.
  - Если места по полу нет, вычисляется по времени.
  - Каждая дистанция одного старта — отдельный зачёт, все учитываются.
- **Биатлон** — дисциплина лыжного рейтинга, та же формула.
- **Эстафета:** та же формула по командам в категории (м/ж/смеш); каждый участник получает полные баллы команды ⏳ подтвердить.
- **Очки RL.**
  - Считаем сами по формуле Кубка Russialoppet: `R = (2 − Tа / Tлидера возрастной группы) × 1000` за марафон (× 500 за полумарафон). Сумма — по **всем** марафонам серии RL за сезон, хранится в `RlPoints`.
  - Готовые суммы со страницы команды не берём: Кубок команд засчитывает только часть результатов (отбор «3×12 + 24»), а спортсмена вне команды RL там нет. Страницы команд Sber Ski Team (`/teams/10235/`, `/teams/10409/`) служат проверкой.
  - РЛ-пункты (рейтинг финишёров, «меньше — лучше») — другая шкала, не используем. Подробности — в [sources.md](sources.md#очки-russialoppet).
  - Марафоны серии RL (`Race.is_rl_series`) по формуле места **не считаются** — иначе один старт учтётся дважды. Они видны в карточке со ссылкой на очки RL.
  - Марафоны вне серии (Grom 50K и т.п.) считаются формулой места.
  - В карточке спортсмена очки RL — отдельная строка «Очки Russialoppet 1524 ÷ 7 = 217,7».
- **⏳ Делитель ÷ 7 — блокирующий вопрос.** Источник — Excel капитана лыж, в ТЗ его нет. Подтверждение методологов по лыжам нужно **до релиза лыж**; пока формула реализуется с `1/7` как константой версии.
- **Сверено с Excel:** формула итога `сумма гонок + RL ÷ 7` воспроизводит колонку «Рейтинг» листа «Участники». Например, у спортсмена A: 2027,1 + 1524/7 = 2244,86. Это значение из кэша исходного файла. В обезличенной копии формулы пересчитываются при открытии и дают другие числа (у спортсмена A — 2508,95).
  - **Откуда разница:** в кэше Excel у части спортсменов пусты ячейки гонок Pioner Cup (18.01.25 и 21.12.25), а при пересчёте VLOOKUP эти результаты находит.
  - **Причина не выяснена:** это может быть устаревший кэш или разница в сравнении строк.
  - **Эталон для тестов:** пересчитанный файл. Какая версия верна ⏳ капитан лыж.
- **Расхождения Excel с ТЗ** (часть формул `100×(1−место/N)`, вес 50 у отдельных этапов, лист смешивает два сезона) — вопросы капитану лыж ⏳. По умолчанию — формула ТЗ.

### 9.3 Триатлон и общий калькулятор «относительно лидера группы»

```
баллы = max(0, (Rmax × (1 − (Tа − Tл) / Tл) + Bmed) × K)
Bmed  = 2 × max(0, Tмед − Tа) в минутах, минуты дробные
```

- Tа — время спортсмена, Tл — лучшее время группы, Tмед — медиана группы.
- Группа = возраст + пол внутри Race. Если возрастных групп нет, группа = пол. Лидер и медиана считаются по всем строкам протокола, в том числе обезличенным (§5).
- Медленнее медианы: `Bmed = 0`. Отрицательный итог: 0. Подтверждено заказчиком.

**Триатлон** — это формула TriStats без `Bgr` и `Kdist` (решение заказчика: иначе нужно пересчитывать протоколы целиком).
- В `breakdown` `Bgr` и `Kdist` записываются как множители = 1. Если их решат включить, менять придётся только калькулятор.
- Правило TriStats «стартовал в PRO — исключён из рейтинга» **не применяем**.
- `Rmax`:

  | Класс | Rmax |
  |---|---|
  | full | 10000 |
  | half | 5000 |
  | olympic | 2500 |
  | sprint | 1250 |
  | supersprint, indoor | 625 |

- `K` — константа формулы по статусу старта `Event.special`: `regular` = 1.0; `worlds` (чемпионат мира) = 1.10; `kona` = 1.15. Значения версионируются через `formula_version`, у старта хранится только статус.
  - Для стартов с ironman.com статус ставится по названию гонки (Kona, World Championship). Способ сбора с ironman.com решим позже (§6.3).
  - Для остальных стартов статус ставит админ или капитан.
- **Эстафета:**
  - лидер и медиана считаются среди команд того же типа (м/ж/смеш);
  - участник получает `баллы команды × этапы / 3`;
  - в зачёт идут все финиши — в смешанных и банковских командах.
  - капитан триатлона упоминает «надбавку за места» в эстафетах ⏳ — размер и правило уточняем. По умолчанию надбавки нет.

### 9.4 Трейл (последний этап MVP)
Полная формула:

```
баллы = max(0, 10 × (км + D+ / 100) × (1 − (Tа − Tл) / Tл) + Bmed)
```

- Тот же калькулятор, что в §9.3: `Rmax = 10 × (км + D+ / 100)`, `K = 1`, `Bmed` считается по группе так же, как в триатлоне.
- **⏳ Скобки.** В ТЗ формула записана с несбалансированной скобкой; мы читаем её как приведённая выше. Подтвердить у заказчика.
- **Без `elevation_gain_m`** гонка незачётная.
- **Очки TopList** (если старт есть на toplist.run) хранятся в `ResultRow.external_points` и показываются в карточке справочно. В рейтинг не идут ⏳ подтвердить у заказчика.

### 9.5 Агрегация
- **Режим:** настройка `aggregation`, по умолчанию `sum_all` — сумма всех стартов за период (решение заказчика: «много бегающий может победить быстро бегающего»). Режим `sum_best_n` остаётся в настройках, но не используется.
- **Равенство баллов:** выше тот, у кого больше лучший одиночный старт, затем у кого больше стартов.
- **Что идёт в рейтинг:** результаты с `ResultLink.status ∈ {auto, confirmed}` спортсменов со статусом `presumed` или `confirmed`, которые на дату старта были сотрудниками (`employee_since..employee_until`). `not_employee` в рейтинг не попадает.
- **Скрытые спортсмены.** Спортсмен с `is_hidden` не показывается ни в одной выдаче. Баллы по нему хранятся, но места в видимой выдаче **пересчитываются без него**, чтобы не оставлять пропусков. В агрегат календаря (§3.4) скрытые входят как числа.
- **Фильтры** не меняют баллы, место пересчитывается внутри выборки:
  - пол;
  - возрастная группа: 18–29, 30–39, 40–49, 50–59, 60+ ⏳.
  Фильтра по подразделению нет.
- **Топ-N без проверки.** Спортсмены `presumed` в топ-N вид × пол попадают в очередь «не проверен» (§3.5); в рейтинге остаются.

### 9.6 Период рейтинга

| Период | Что это | Где |
|---|---|---|
| `rolling` (по умолчанию) | последние 365 дней от сегодня | все; пересчёт каждую ночь + снимок для динамики места |
| срез на дату | 365 дней до выбранной даты | капитан и админ; считается на лету |
| календарный год | 1 января – 31 декабря | архив для бега, триатлона, трейла |
| лыжный сезон | 1 ноября – 30 мая, подпись «2026/27» | архив для лыж; очки RL берутся за соответствующий сезон RL |

В окне `rolling` очки RL учитываются за сезон RL, который пересекается с окном. Если окно захватывает два сезона, берётся последний ⏳ уточнить у капитана лыж.

### 9.7 Проверка формул
- **Golden-тесты.** Эталонные таблицы заказчика превращаются в golden-тесты, расхождение больше 0.5 балла — ошибка.
- **Лыжный Excel** — промежуточная версия с ошибками, поэтому годится как ориентир, а не как точный эталон:
  - тестами фиксируется формула итога (сумма + RL ÷ 7);
  - отдельные расхождения разбираются с Лизой.
- **Беговой рейтинг** (Google-таблица) запрашиваем ⏳.

Карточку «Как считается лыжный рейтинг» привести к формулам §9.2 |

**Как посчитано — формулы и легенда:**

| Вид | Формула | Подпись |
|---|---|---|
| Бег | `норматив / время × 1000` | Нормативы по году, дистанции и полу |
| Лыжи и биатлон | `100 × (N − место + 1) / N`; плюс очки Russialoppet ÷ 7 | Плюс очки Russialoppet ÷ 7 (⏳ подтверждение методологов, §9.2) |
| Триатлон | `(Rmax × (1 − (Tа − Tл) / Tл) + Bmed) × K` | Относительно лидера группы |
| Трейл | `10 × (км + D+ / 100) × (1 − (Tа − Tл) / Tл) + Bmed`, K = 1 | Без набора высоты не считается |

Легенда: **Tа** — время спортсмена; **Tл** — время лидера группы; **Tмед** — медиана группы; **Bmed** — бонус за обгон медианы, `2 × max(0, Tмед − Tа)` в минутах; **K** — коэффициент статуса старта (обычный 1.0, ЧМ 1.10, Кона 1.15); **Rmax** — максимум баллов класса дистанции; **D+** — набор высоты, м; **N** — число финишёров того же пола на дистанции.

**Календарь (бывшие «Старты»):**
- Показывает по месяцам прошедшие и будущие старты; фильтр по виду спорта.
- У запланированных — плашка «запланирован».
- Колонка «Сотрудников в прошлом выпуске» и разбивка по дистанциям. Только числа, без списков людей.
- Для капитана (свои виды спорта) и админа — кнопка «Добавить запланированный старт» (название, город, вид спорта, ориентировочные даты, дистанции) и подтверждение серии.
- Бюджета и квот слотов нет.

## 11. API (контур)

Все маршруты, кроме `/api/auth/*`, требуют сессии. Бывший `/api/public/*` переименован в `/api/app/*` и доступен любому активному пользователю.

```
POST /api/auth/register                              (создаёт User со status=pending)
POST /api/auth/login | /logout
POST /api/auth/password-reset/request                (email → письмо со ссылкой)
POST /api/auth/password-reset/confirm                (token + новый пароль, токен одноразовый)
GET  /api/auth/me                                    (роль, статус, athlete_id, виды спорта)

GET  /api/app/ratings?sport=&period=rolling|2026|ski_2026_27&gender=&age_group=&q=
GET  /api/app/athletes/{id}
GET  /api/app/athletes/{id}/scores/{score_id}
GET  /api/app/events?sport=&period=
GET  /api/app/events/{id}
GET  /api/app/calendar?from=&to=&sport=              (прошедшие и planned; только агрегаты по сотрудникам)
POST /api/app/reports                                (kind: not_me|add_start|other_club|hide_me|link_me|data_error)

GET  /api/captain/ratings?…&as_of=                   (+ полная ДР и отчество)
GET  /api/captain/ratings/export.xlsx?…
GET  /api/captain/athletes/{id}/export.xlsx

GET  /api/admin/dashboard                            (капитан — в рамках своих видов спорта)
GET  /api/admin/access-requests?status=pending       POST /api/admin/access-requests/{user_id}/decision
                                                     (approve{athlete_id?} | reject; админ и капитан)
GET  /api/admin/moderation?status=pending       POST /api/admin/moderation/{link_id}/decision
GET  /api/admin/reports?status=new              POST /api/admin/reports/{id}/decision
GET  /api/admin/verify-queue                         (топ-N без confirmed)
CRUD /api/admin/athletes  (+ POST /merge, POST /{id}/unlink/{link_id}, POST /import, POST /{id}/search-starts,
                           PATCH /{id}/employee-status, PATCH /{id}/hidden)
CRUD /api/admin/events    (+ POST /merge, PATCH /races/{id})
POST /api/admin/events/planned                       (запланированный старт)
GET  /api/admin/series/suggest?event_id=             POST /api/admin/events/{id}/series  (привязка серии)
GET  /api/admin/events/{id}/duplicates               (planned ↔ done)
POST /api/admin/uploads → PATCH /uploads/{id}/mapping → POST /uploads/{id}/import
GET  /api/admin/sources   POST /api/admin/sources/{code}/run                 (только админ)
GET  /api/admin/club-report                                                   (только админ)
GET/PUT /api/admin/settings/*                                                 (только админ)
CRUD /api/admin/users     (+ POST /{id}/block, POST /{id}/reset-password, PUT /{id}/sports)   (только админ)
DELETE /api/admin/events/{id}/protocol                                        (только админ)
```

**Авторизация:**
- Сессионная cookie (HttpOnly, SameSite=Lax, Secure), пароли argon2. Роль и статус проверяются на роутере.
- Роутер `captain/*` — роли `captain` и `admin`; запись в `admin/*` для капитана ограничена по видам спорта (`CaptainSport`), остальное — только `admin`.
- Состояния `pending`, `blocked`, `rejected` получают только `/api/auth/me` и `/api/auth/logout`.
- CSRF-защита запросов с cookie (§12). `POST /reports` и `/auth/*` ограничены по частоте.
- Нет ответов, в которых имя, ДР или отчество неактивного пользователя видны без входа.

## 12. Нефункциональные требования

- **Надёжность сбора:** падение одного адаптера не останавливает остальные; до 3 повторов; журнал хранится 90 дней.
- **Бэкапы:** ежедневный `pg_dump`, хранение 14 дней + копия вне VM. Бэкапы подчиняются тем же правилам ПДн и хранятся в РФ.
- **Наблюдаемость:** структурные логи (JSON), страница статусов.
  - Telegram-бот только для админа: ежедневная сводка и срочные сообщения (адаптер упал или вернул 0 записей, перевод в `not_employee`). Вход через Telegram не используется.
- **Безопасность аутентификации:**
  - пароли argon2; политика: минимум 10 символов, проверка по списку частых паролей ⏳;
  - cookie HttpOnly, SameSite=Lax, Secure; CSRF-токен для запросов с cookie;
  - ограничение частоты входа и регистрации по IP и по учётке; после 5 неудачных попыток блокировка на 15 минут (`failed_logins`, `locked_until`);
  - токены сброса пароля: одноразовые, хранятся хэшем, TTL 1 час ⏳; админский сброс использует тот же механизм;
  - ответ на запрос сброса и на вход не раскрывает, существует ли email;
  - срок жизни сессии и принудительный выход при блокировке учётки.
- **Общая безопасность:**
  - HTTPS (Caddy), секреты в `.env`;
  - `AuditLog` на действия администратора и капитана, включая выгрузки в Excel;
  - `noindex` — дополнительная защита, не контроль доступа;
  - браузерный контейнер без доступа к БД, только к API очереди.
- **Персональные данные (минимизация):**
  - в БД: Фамилия, Имя, Отчество, ДР, город, email — для зарегистрированных пользователей и спортсменов рейтинга; пользователю показываются только Фамилия, Имя и год рождения (§2);
  - строки несотрудников обезличиваются после окна сопоставления (§5);
  - сырые ответы источников удаляются через `raw_ttl_days` (по умолчанию 90), новых сотрудников ищем повторным запросом;
  - выгрузки в Excel — только капитану и админу, каждая пишется в `AuditLog`;
  - согласие на обработку ПДн: чекбокс при регистрации, `consent_at` и `consent_version`; текст политики версионируется, при новой версии требуется повторное согласие ⏳; владелец текста — ⏳ заказчик;
  - правовое основание для показа спортсменов, не зарегистрированных в системе: показываем с возможностью «скрыть меня» ⏳ юристы заказчика.
- **Хостинг:** российское облако (cloud.ru или Yandex Cloud) с аттестацией по 152-ФЗ, одна VM, данные в РФ ⏳ согласование с ИБ заказчика. Нужен исходящий доступ к источникам и SMTP.
- **Почта:** SMTP для сброса пароля и уведомлений о решении по заявке; доставка на корпоративные адреса ⏳ заказчик (§13).
- **Производительность:** страницы отвечают за 300 мс и быстрее; ночной пересчёт окна `rolling` занимает минуты.
- **Доступность:** WCAG AA в обеих темах, `prefers-reduced-motion`.
- **Тесты:**
  - юнит-тесты калькуляторов и сопоставления;
  - фикстуры адаптеров (для `browser` — сохранённый HTML);
  - golden-тесты рейтингов;
  - API-тесты, включая проверку ролей, скоупа капитана по видам спорта и статусов учётки;
  - тесты обезличивания и TTL;
  - смоук экранов в обеих темах.

## 14. Разрыв между кодом и спекой

Текущее приложение запущено только локально, срочных правок нет; разрыв закрывается задачами в бэклоге. Подробный разбор с файлами, бэклогом эпиков, критериями приёмки и рисками — в [SPEC-v1.3-gap.md](SPEC-v1.3-gap.md). Краткое состояние кода на 2026-11-18:

| Область | Сейчас в коде | Нужно по v1.3 |
|---|---|---|
| БД | веб-приложение на SQLite (агент-ревью — через `DATABASE_URL` в Postgres), парсеры на Postgres 16; в `feature/auth` веб уже на Postgres (asyncpg) | единый Postgres 16 |
| Деплой | нет Dockerfile, деплоя и CI | docker compose в РФ-облаке (§4.1) |
| Авторизация | в рабочей ветке нет; в несмёрженной `feature/auth` — прототип: роутеры закрыты, но учётки `user/user` и `admin/admin` зашиты в код, пароли открытым текстом | регистрация, вход, роли, сессии, модерация заявок (§3.1, §11, §12) |
| Баллы | считается только бег (`run-v1`, нормативы только 2026, 24 ч не считается) | лыжи, триатлон, трейл, RL; нормативы по годам; `formula_version` |
| Экран «Как посчитано» | только бег, вкладки лыж, триатлона, трейла отключены | формулы четырёх видов с легендой (§10.2) |
| ПДн | в SQLite нет отчества, ДР и признака сотрудника; в Postgres хранятся все участники протоколов; профиль показывает город и клуб; протокол старта открыт со всеми участниками | `employee_status`, отчество, ДР; обезличивание и TTL; карточки без города и клуба; протокол старта только с сотрудниками (§5, §10) |
| Календарь | нет планируемых стартов и счётчика сотрудников | `EventSeries`, `Event.status`, экран «Календарь» (§3.4) |
| Подразделения, ЛК | нет | не делаем |
| Telegram | кода нет | только алерты админу |
| Пьедестал | убран в коде (ADR 0002) | убран; в README описан ошибочно, исправить |
| README | трейл без `Bmed`, пьедестал, открытый доступ | привести к v1.3 |
