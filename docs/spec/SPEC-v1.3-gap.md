# Разрыв: текущий код ↔ SPEC v1.3

Версия 2026-11-18. Для команды разработки. Код: `czczczt/sports-agent`, рабочая ветка `dev` (объединены React-интерфейс, asyncpg PostgreSQL, закрытие роутеров и спеки). Спека: [SPEC.md](SPEC.md) v1.3, предыдущая — [SPEC-v1.2.md](SPEC-v1.2.md).

Размер: S — до 2 дней, M — до 1 недели, L — больше недели.

## 1. Состояние кода

Есть:
- Парсеры бега (`parser_running/`, Postgres 16, `docker-compose.yaml` поднимает только `db`) и биатлона с OCR (`parser_biathlon/`).
- Веб-приложение FastAPI (`app/`) на SQLite (`app/db.py`, `SQLITE_DB_PATH`); отдельно экран подтверждения правок агента ходит в Postgres парсера (`app/agent_review.py`, `app/mcp_agent/orchestrator.py:28-33`). То есть приложение уже работает с двумя БД.
- React SPA (`frontend/`): рейтинг, поиск, профиль, старты, протокол, «Как посчитано» (только бег), экран агента.
- Рейтинг бега за 365 дней, `sum_all`, тай-брейки (`app/services/rating_service.py`, `FORMULA_VERSION = "run-v1"`, нормативы `_NORMS` зашиты в код).

Нет:
- Авторизации и ролей вообще: роутеры `app/api/*.py` открыты, `/api/agent-review` тоже.
- Баллов лыж, триатлона, трейла, очков RL: `parser_running/scoring.py:52` возвращает `unsupported_sport`; в UI вкладки отключены (`RatingPage.tsx:46-48`).
- Статуса сотрудника, отчества, полной даты рождения у спортсмена, заявок, календаря планируемых стартов, `EventSeries`.
- Dockerfile, CI, деплоя; приложение работает только локально. Telegram-кода нет.

В ветке `dev` (коммиты поверх React, объединена с актуальными спеками):
- Веб-приложение переведено на Postgres через `asyncpg` (`app/db.py`), SQLite убран.
- Все `/api/*`, кроме `/api/auth`, и `/api/agent-review` закрыты зависимостью `get_current_user` (`app/main.py:46-54`); модалка входа и `AuthContext` во фронтенде; `tests/test_auth.py`.
- Это прототип, не модель v1.3: две учётки зашиты в код (`user/user`, `admin/admin`, `app/api/auth.py` `USERS_DB`), пароли в открытом виде, нет таблицы пользователей, регистрации, роли капитана, блокировки и сброса; самописный HMAC-токен на 7 дней, отзыв хранится в памяти процесса; `AUTH_SECRET_KEY` по умолчанию случайный, после рестарта все сессии слетают.

## 3. Бэклог (в порядке реализации)

### 0. Единая БД Postgres и деплой-основа
Зависит: — (стартовать от `dev`: переход на asyncpg там уже сделан; остаются Alembic, перенос данных, контейнеры, CI)
- Цель: веб-приложение работает на Postgres 16 вместе с парсерами; есть Alembic, Dockerfile, compose, CI.
- Приёмка: `docker compose up` поднимает api+db без SQLite; Alembic создаёт схему с нуля; данные `athlete`/`result_athlete` перенесены скриптом, счётчики до/после совпадают; рейтинг бега даёт те же места, что до переноса (тест); CI прогоняет тесты на Postgres.
- Модули: `app/db.py`, `app/config.py`, `init_athletes.py`, `app/services/*`, `agent_review.py`, `docker-compose.yaml`.

### 1. Auth, пользователи, заявки на доступ
Зависит: 0. Заменяет прототип из `dev`: `USERS_DB` и открытые пароли удалить, гард роутеров и `AuthContext` оставить.
- Цель: вход email+пароль, регистрация с согласием, роли user/captain/admin, модерация заявок.
- Приёмка: неавторизованный запрос к любому `/api/*` кроме auth даёт 401 (тест по всем роутерам); пароль хранится argon2; после N неудачных попыток вход блокируется; сброс по ссылке из email работает на тестовом SMTP; заявка одобряется админом или капитаном, до одобрения учётка не видит данных; blocked не входит; регистрация без чекбокса согласия отклоняется; каждое действие админа пишет AuditLog.
- Модули: новый `app/core/auth`, `app/api/auth.py`, все роутеры (зависимость), `frontend/` (вход, регистрация, сброс, гард маршрутов).

### 5. Очередь «топ-N без проверки»

### 6. Формулы: лыжи, триатлон, трейл, RL
Зависит: 0; блокер лыж — ответ методологов по RL÷7

## 4. Быстрые правки документации (README.md)

## 5. Риски

- Сейчас без входа доступны ФИО, ДР и клуб всех участников протоколов. Пока приложение только локальное, но деплой до задач 1–2 недопустим, в том числе с прототипом `dev`: учётки `user/user` и `admin/admin` известны всем.
- Смена БД (задача 0) блокирует всё остальное; нужно сначала решить судьбу двух БД и кэша `athlete_assessment_cache`.
- RL÷7: источник только Excel капитана лыж; без ответа методологов лыжи нельзя выпускать.
- Расхождение кэша и пересчёта в лыжном Excel (v1.2 §9.2) делает эталон неоднозначным.
- Правовое основание показа незарегистрированных сотрудников (по умолчанию показываем, «скрыть меня» по заявке) не согласовано с юристами.
- Корпоративная почта может не пропустить письма сброса; SMTP-доставляемость надо проверить рано.
- Трактовка скобок формулы трейла не подтверждена заказчиком.
- Облако и аттестация 152-ФЗ зависят от ИБ заказчика; сроки неизвестны.
- Автопривязка учётки по ФИО+ДР при тёзках: только с подтверждением модератора.
