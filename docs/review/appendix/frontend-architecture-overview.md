# Обзор архитектурных вариантов фронтенда (для владельца)

Цель: освежить картину и выбрать стек для дашборда рейтинга (8 страниц, FastAPI JSON API, команда студентов + AI-агент). Контекст проекта: ~3 800 строк, URL-фильтры, 2 графика, 2 сложных поля ввода, 1 экран с мутациями (правки агента), тема светлая/тёмная на CSS-токенах.

Каждый раздел: варианты → плюсы/минусы → когда брать → вывод для нас.

---

## 1. Организация кода

### 1.1 По типам (components / hooks / pages) — текущая

```
src/
  components/  hooks/  pages/  lib/  api/  styles/
```

- Плюсы: ноль порога входа, привычно, мало папок.
- Минусы: всё про одну фичу размазано по 4-5 каталогам; `components/` превращается в свалку; нет границ — любой импортирует любого; AI-агент кладёт код «куда придётся».
- Когда: прототип, до ~10 страниц и 1-2 разработчиков.
- Наш случай: на нём мы сейчас, и первые признаки есть (`ui/index.tsx` на 8 компонентов, `useApi` без домена).

### 1.2 Feature-based / modules

```
src/
  features/
    rating/        {api, components, hooks, RatingPage.tsx, index.ts}
    athletes/
    events/
    agent-review/
  shared/          {ui, lib, api, config}
  app/             {router, providers}
```

- Плюсы: изменение фичи — в одной папке; понятная зона ответственности; легко удалить/вынести; хорошо работает с AI (контекст = папка).
- Минусы: нужно правило «фича не импортирует фичу» (иначе спагетти); спорно, куда класть общие сущности (спортсмен, старт используются в нескольких фичах).
- Когда: 5-50 экранов, 2-10 разработчиков.

### 1.3 Bulletproof-react (Alan Alickovic)

Это feature-based + строгие правила: `features/*` не импортируют друг друга, однонаправленный поток `shared → features → app`, внутри фичи `api/components/hooks/stores/types/utils`, проверяется ESLint-правилом `import/no-restricted-paths`.

```
src/
  app/            routes/ provider.tsx router.tsx
  components/     общие ui
  features/       <feature>/{api,components,hooks,types,utils}
  hooks/ lib/ types/ config/ testing/ stores/
```

- Плюсы: описан, популярен, есть эталонный репозиторий (знает и ИИ); правила проверяются линтером.
- Минусы: каталог `features/x/api|components|hooks` — много мелких папок на маленькую фичу; общие сущности — та же дилемма.
- Когда: хотите «feature-based, но без FSD-терминологии».

### 1.4 Feature-Sliced Design (FSD)

Слои (сверху вниз; импорт только вниз): `app → pages → widgets → features → entities → shared`. Внутри слоя — слайсы (папки по домену), внутри слайса — сегменты (`ui`, `model`, `api`, `lib`, `config`). Слайс экспортирует только через публичный API (`index.ts`); слайсы одного слоя друг друга не импортируют. Проверка: линтер `steiger` (официальный) или `eslint-plugin-boundaries`/`@feature-sliced/eslint-config`.

```
src/
  app/        providers/ router/ styles/
  pages/      rating/ athlete/ events/ event/ race/ agent-review/ search/
  widgets/    protocol-table/ athlete-header/ rating-table/
  features/   search-athlete/ filter-events/ agent-decision/ ai-assessment/
  entities/   athlete/ event/ race/ rating/   {ui,model,api,lib}
  shared/     ui/ api/ lib/ config/
```

- Плюсы: жёсткие границы (подходит студентам + ИИ: проверка автоматическая, `steiger` падает на нарушении); однозначный ответ «куда положить»; масштабируется.
- Минусы: выше порог входа и церемония (слои, сегменты, public API); на 8 страницах слои `widgets` и `entities` часто пустые или искусственные; терминологию надо объяснять; риск «FSD ради FSD».
- Когда: 20+ экранов, несколько команд, долгая жизнь; или команда уже знает FSD. (У владельца в других проектах FSD используется — это плюс к знакомству.)

### 1.5 Atomic Design (atoms/molecules/organisms/templates/pages)

Классификация UI-компонентов по размеру, а не организация приложения.

- Плюсы: удобно для дизайн-системы и сториз.
- Минусы: границы между molecule/organism размыты, спорят о каждом компоненте; не отвечает на вопрос «где логика и данные».
- Когда: если строите UI-кит. Для приложения — как подсказка внутри `shared/ui`, не как корневая структура.

### 1.6 Сравнение и вывод

| | По типам | Feature | Bulletproof | FSD | Atomic |
|---|---|---|---|---|---|
| Порог входа | очень низкий | низкий | средний | высокий | средний |
| Границы проверяются линтером | нет | можно | да | да (steiger) | нет |
| Подходит для AI-агента | слабо | хорошо | хорошо | очень хорошо (правила жёсткие) | слабо |
| Масштаб | до ~10 стр. | до ~50 | до ~50 | 50+ | UI-кит |

**Уместно для дашборда среднего размера:** feature-based (bulletproof-вариант) либо «FSD-lite» — три слоя `app / pages / features / shared` без `widgets` и `entities` до тех пор, пока не появится повторное использование между фичами. Полный FSD — если владелец хочет единый подход со своими другими проектами.

## 2. Декомпозиция компонентов

**Container/presentational (классика).** Контейнер получает данные, презентационный — только props. Сегодня то же достигается проще хуками: `useAthleteProfile()` (данные и действия) + `<AthleteProfileView/>` (разметка). Отдельные «контейнеры» нужны только когда разметку хочется тестировать/показывать в Storybook без сети.

**Логика в хуках.** Выносить хук, когда: (а) логика > ~15 строк и не про разметку, (б) нужна повторно, (в) есть эффекты/подписки. Не выносить «ради красоты» одну строку `useState`.

**Compound components.** Родитель + `Parent.Child` через контекст (`<Tabs><Tabs.List/>…`). Брать для составных виджетов (карточка, таблица с header/row, модалка), где пользователь компонует части. Для нас: `Card` (head/body/foot — сейчас через CSS-классы), `Table`.

**Композиция через children/slots.** Предпочтительнее набора булевых props (`inCard`, `icon={null}` как в `EmptyState`/`Loader`). Правило: если props с «режимами» > 3 — передавать `children`/слоты (`header`, `actions`).

**Размер.** Ориентиры (не догма): компонент ≤ 150 строк, ≤ 5 `useState`, ≤ 7 props; файл — один экспортируемый компонент; больше — делить по ответственностям (данные/действия/разметка), а не по строкам.

**Colocation.** Держать рядом то, что меняется вместе: компонент, его CSS Module, тест, хук, типы. Поднимать «выше» только при реальном втором потребителе.

**Антипаттерны (видны в проекте):** страница, в которой запросы, парсинг URL и разметка; `render-prop` для состояний; два варианта списка на один набор данных.

## 3. Состояние: что где хранить

| Вид | Что это | Инструмент | Пример у нас |
|---|---|---|---|
| Server state | Данные с бэка, кэш, повторные запросы | **TanStack Query** | рейтинг, спортсмен, старты |
| URL state | То, чем хотят делиться и что должно переживать reload/назад | search params (`useSearchParams`, `nuqs`, TanStack Router) | фильтры, поиск, пол, дистанция |
| Form state | Черновик ввода до отправки, валидация | `useState` для 1-3 полей; **react-hook-form + zod** для сложных | форма решения по правке агента |
| Client UI state | Локальное, эфемерное | `useState`/`useReducer` рядом с компонентом | раскрытие отчёта, busy |
| Global client state | Нужно далёким компонентам и не лежит в URL/сервере | Context (редко меняется) / **Zustand** / Jotai / Redux Toolkit | тема |

Сравнение глобальных:
- **Context** — встроен; плох для часто меняющегося (перерендер всех потребителей); для темы, локали, текущего пользователя — отлично.
- **Zustand** — минимальный API, селекторы, без провайдеров; брать, если нужен настоящий клиентский стор.
- **Jotai** — атомарно, хорош для множества независимых мелких состояний.
- **Redux Toolkit** — много церемоний; брать при сложных потоках, devtools/time-travel, команде с опытом Redux. Для нас избыточен.

**Правило:** сначала спросить «это есть на сервере?» → Query. «Должна ли ссылка это воспроизводить?» → URL. «Это черновик до submit?» → форма. «Нужно ли двум далёким частям?» → Context/Zustand. Иначе — локальный `useState`. Не дублировать серверные данные в Zustand/`useState`.

## 4. Стили

| Вариант | Плюсы | Минусы | Когда брать |
|---|---|---|---|
| Plain CSS + CSS vars (сейчас) | ноль зависимостей, токены уже есть | глобальные коллизии, нет связи компонент-стиль, растёт в «простыню» | прототип |
| **CSS Modules** | изоляция, ноль runtime, вся мощь CSS, просто для студентов, работает с токенами | нет «утилит»; нужно придумывать имена; нет готовых компонентов | **сохраняем дизайн-систему и токены** |
| Tailwind (+ shadcn/ui, cva) | быстрые итерации, единый словарь, ИИ пишет хорошо; shadcn даёт доступные примитивы (Radix) в вашем коде | длинные className, нужна дисциплина (cva/`cn`), миграция существующей вёрстки (~900 строк CSS + токены) | команда любит утилиты, дизайн-система ещё не устоялась |
| CSS-in-JS (styled-components, emotion) | колокация, динамические стили | runtime-стоимость, проблемы с RSC/streaming, поддержка styled-components замедлилась; сообщество уходит к zero-runtime | не брать в новых проектах |
| vanilla-extract / Panda / StyleX | типобезопасные стили, ноль runtime | выше порог входа, свой DSL | большие дизайн-системы с типизацией токенов |
| UI-киты: Mantine, MUI, Chakra, AntD | готовые компоненты, формы, доступность из коробки, быстрый старт | свой визуальный язык (перебивает ваш `theme.css`), вес, переопределение тем; AntD/MUI тяжёлые | админки/внутренние инструменты без требований к уникальному дизайну |

Для команды студентов: самый безопасный путь — **CSS Modules + существующие токены** (минимум нового, есть готовая дизайн-система ADR-0001). Tailwind+shadcn — быстрее наращивать, но требует переписать вёрстку и перетащить токены в `@theme`. Mantine — если дизайн не критичен (рейтинг — публичная витрина, дизайн важен, поэтому киты нежелательны).

## 5. Типизация API

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| Ручные типы (сейчас) | `types.ts` по pydantic-моделям | нет инструментов | дрейф неизбежен, нет проверки в CI |
| **openapi-typescript + openapi-fetch** | генерирует `schema.d.ts` (только типы) + крошечный типизированный fetch (6 КБ) | типы путей, параметров и ответов; ноль runtime-кода кроме клиента; идеально с TanStack Query через `openapi-react-query` | ответы не валидируются в рантайме; клиента `Query` пишете сами (или `openapi-react-query`) |
| Orval | генерит клиенты + готовые хуки TanStack Query + (опц.) zod и MSW-моки | меньше ручного кода, моки для тестов | больше сгенерированного кода, тяжелее конфиг |
| hey-api (`@hey-api/openapi-ts`) | SDK + типы + плагины (TanStack Query, zod) | активно развивается, гибкий | относительно молодой, частые изменения API |
| tRPC/GraphQL | — | — | не применимо к FastAPI |

**Рекомендация:** `openapi-typescript` + `openapi-fetch` (+ `openapi-react-query` при Query). Скрипт `npm run gen:api` читает `/openapi.json` бэка и пишет `src/shared/api/schema.d.ts` (в `generated/` — не править руками, коммитится); CI запускает генерацию и падает на diff. Orval — если захотите автогенерацию хуков и MSW-моков. Условия на бэке: у всех эндпоинтов `response_model` (у agent-review сейчас нет — добавить), enum как `Literal`/`Enum`, а не `str`.

## 6. Роутинг, сборка, тулинг

### Роутинг

- **React Router v7 (library/data mode)** — продолжение RR6 (апгрейд `react-router-dom@6 → react-router@7` почти без изменений); loaders/actions необязательны. Плюсы: знаком, минимум переписывания, SPA-режим. Минусы: типобезопасность параметров/search params слабее; в framework-режиме тянет к SSR.
- **TanStack Router** — полная типобезопасность путей, params и search params (валидация через zod), встроенные loaders с интеграцией с Query, авто-code-splitting плагин. Минусы: меньше распространён, свои абстракции, файловая генерация роутов; студенты и ИИ знают хуже.

Выбор: у нас 8 маршрутов и **URL-state — главный механизм фильтров**. Если нужна типобезопасная работа с search params «из коробки» — TanStack Router; если важна простота и знакомство — RR7 + `nuqs`/zod-хелпер. Рекомендую RR7 (меньше риска), TanStack Router — как осознанный вариант «enterprise».

### Сборка и инструменты

- **Vite** — оставить (нет причин менять). Обновить до Vite 6/7 по плану.
- **ESLint flat config** (`eslint.config.js`) + `typescript-eslint` + `eslint-plugin-react-hooks` + `jsx-a11y` + `boundaries`/steiger. **Prettier** — форматирование. Альтернатива: **Biome** (быстрый, всё в одном, но слабее экосистема плагинов: нет аналога boundaries, правила a11y/react-hooks покрыты частично). Выбор: ESLint+Prettier, если нужны границы импортов и зрелые a11y-правила; Biome — если скорость и простота важнее.
- **Vitest + Testing Library** (+ **MSW** для сетевых моков) — юнит/компонентные тесты. **Playwright** — 3-5 сквозных сценариев (поиск → профиль, рейтинг с фильтром, правки агента). **Storybook** — по желанию для `shared/ui`; на 8 страницах не обязателен, полезен, если будут расти компоненты и работать несколько студентов.
- **CI:** typecheck, lint, test, build, `gen:api` без diff.

## 7. Итоговая рекомендация

### Вариант A — минимальный («навести порядок, не переписывая»)

- Оставляем: Vite, React Router, plain CSS + токены, Chart.js, структуру по типам.
- Добавляем: ESLint + Prettier, Vitest + RTL (несколько тестов), CI, `openapi-typescript` (типы генерятся), lazy-страницы, `errorElement`, self-host шрифты.
- Убираем inline-стили из страниц, дубль списков.
- Плюсы: 3-5 дней, нулевой риск. Минусы: `useApi` остаётся, структура по типам продолжит расти.

### Вариант B — рекомендуемый

- Структура: **feature-based / FSD-lite** (`app / pages / features / shared`, границы линтером).
- Данные: **TanStack Query** + **openapi-fetch** (типы из OpenAPI).
- URL-state: `useSearchParams` + zod/`nuqs`; формы: `useState`, где 1-3 поля, **react-hook-form + zod** на экране правок агента.
- Стили: **CSS Modules + текущие токены `theme.css`**; нативные `input type=date`, убрать Air Datepicker.
- Роутинг: **React Router 7** (lazy-страницы, `errorElement`).
- Графики: Chart.js, тонкая обёртка; конфиги — чистые функции.
- Тулинг: ESLint flat + Prettier, Vitest + RTL + MSW, Playwright smoke, CI.
- Плюсы: убирает все H-проблемы аудита, остаётся близко к текущему коду, понятно студентам и ИИ. Минусы: 2-3 недели рефакторинга; новые библиотеки для изучения.

### Вариант C — «enterprise»

- Полный **FSD** (`steiger` в CI), **TanStack Router** (типобезопасные search params, loaders) + **TanStack Query**, **orval/hey-api** (хуки и zod из схемы), **Tailwind + shadcn/ui + cva** либо vanilla-extract, **Storybook** + визуальные тесты, Playwright на CI, **Biome** или ESLint+Prettier, `knip`, `size-limit`, Renovate.
- Плюсы: масштабируемо, максимум автоматизации. Минусы: переписывание стилей и роутинга, высокий порог для студентов; избыточно для 8 страниц.

**Моё решение:** B. A — как фаза 0 (инфраструктура), которая делается всё равно и не противоречит B. C — только если проект вырастет до 20+ экранов или появится вторая команда.
