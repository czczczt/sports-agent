# Аудит: парсер, агент и чтение рейтинга (состояние на ветке `master`, 0617de6)

Только описание того, как устроено сейчас. Целевая архитектура — [agent-service-architecture.md](agent-service-architecture.md).
Ссылки `файл:строка` даны для коммита выше; пути относительно корня репозитория.

## 0. Главное за минуту

1. Парсер и сайт живут в **разных базах**: парсер пишет в PostgreSQL (`parser_running/db.py`), сайт читает SQLite `running.db` (`app/db.py:37-45`). Рейтинг, который видит пользователь, считается из SQLite (`app/services/rating_service.py:165`), а не из того, что собирает `run.py`. Мост между базами — одноразовый `migrate_sqlite.py` в обратную сторону (SQLite -> PG), прямого пути «PG -> сайт» нет.
2. Ни один HTTP-эндпоинт **не запускает** парсер или агента. `run.py`, `dedup.py`, `scoring.py`, `agent_queue.py process` — ручные CLI. «Блокировка основного потока API» сейчас сводится к трём местам (раздел 1.4) и к тому, что произойдёт, когда студенты подключат `run.py` к API «как есть».
3. `run.py` держит **одну транзакцию на весь старт**, включая HTTP-запросы всех его дистанций (`parser_running/run.py:72-165`). Это долгие блокировки строк и «idle in transaction» на 10+ минут.
4. Кеш HTTP **вечный** (`parser_running/http_cache.py:29`): повторный прогон никогда не обновит уже скачанный протокол. Для фонового обновления это блокер.
5. Рейтинг на сайте после первого запуска **не обновляется**: спортсмены склеиваются из результатов один раз и только если таблица `athlete` пуста (`app/main.py:22-29`, `init_athletes.py:89-93`).
6. Слой «агент» — это три разных вещи, из которых в бою работает одна (раздел 2).

## 1. Как сейчас запускается и где блокируется

### 1.1. Кто что запускает

| Что | Как запускается | Где |

| Дедуп | `python dedup.py` (отдельно, руками) | `parser_running/dedup.py:79-135` |
| Баллы | `python scoring.py --seed --recalculate` | `parser_running/scoring.py:218-242` |

| Спортсмены сайта | при старте API, только если `athlete` пуста | `app/main.py:22-29` |
| Агент-ремонтник | `python agent_queue.py process <id>` | `parser_running/agent_queue.py:291`, `:760` |

Cron, планировщика, очереди задач и контейнера для воркера нет. `docker-compose.yaml` поднимает только `db` (комментарий в начале файла: «Сервис agent добавит инфраструктура»). В `docs/agent-queue.md:116-117` фоновый обработчик прямо назван открытым вопросом («`procrastinate` по SPEC»).

### 1.2. Поток данных парсера (последовательный)

`run.py:main` -> `conn.competitions()` (список стартов) -> для каждого старта **по очереди** `conn.races(comp)` -> для каждой дистанции **по очереди** `conn.results(comp, race)` -> `store.save_*` -> `con.commit()` в конце старта. Распараллеливания нет вообще: ни по площадкам (одна площадка на процесс, `--source`), ни по стартам, ни по дистанциям.

Задержки — `time.sleep(0.5)` перед каждым запросом (`http_cache.py:34`, `rr_platform.py:43`) плюс при ошибках `sleep(5 * n)` (`http_cache.py:41`). 10+ минут складываются из: ~N стартов x ~M дистанций x 1-30 страниц x (0.5 с + время ответа; у `runc` ответ бывает дольше минуты, E23).

То есть звено «баллы -> рейтинг» в PostgreSQL заканчивается таблицей `score`; таблиц `athlete`, `result_athlete`, `rating` в PG нет. Автоматического пути «собрал -> сопоставил -> пересчитал -> показал» в проекте нет ни в одной из баз.

### 1.4. Где реально блокируется поток / event loop

1. **Старт API** (`app/main.py:20-37`): `setup_schema`, возможный `populate_athletes` (группировка всех результатов в Python, `init_athletes.py:75+`) и `recalculate_rating` выполняются синхронно в `lifespan` до `yield`. Пока идёт — сервер не принимает запросы. `recalculate` читает **все** результаты в память (`rating_service.py:194-205`, `fetchall()`), удаляет и вставляет заново в одной транзакции (`:183-283`).
2. **`async def` эндпоинт с синхронным SQLite внутри** (`app/api/athletes.py:61-70` -> `app/services/agent_service.py:172-250`): `conn.cursor().execute(...)` и `compute_athlete_metrics` блокируют event loop; плюс на каждый запрос заново берётся OAuth-токен GigaChat (`agent_service.py:51-65`, кеша токена нет) — 2 HTTP-вызова на спортсмена без кеша.
3. **`POST /apply`** (`app/agent_review.py:222-235`) — обычный `def`, значит поток из пула, но он делает `git worktree add`, перезапуск коннектора и `git push` синхронно в запросе; `docs/agent-queue.md:116` отмечает то же.
4. Остальные эндпоинты (`def`, SQLite) выполняются в threadpool Starlette и сами по себе не блокируют loop.

Если запускать `run.py` из API как есть (`subprocess` или функция в `def`-эндпоинте): CLI-процесс в отдельном процессе не блокирует API, но гоняет две базы; импортированная в процесс API функция `run()` займёт поток пула на минуты и держит открытую транзакцию PG.

### 1.5. Чтение рейтинга и неконсистентность

`GET /api/rating` (`app/api/rating.py:13-30`) -> `get_rating_page` (`rating_service.py:296-374`):
- период выбирается запросом `ORDER BY period_end DESC LIMIT 1` (`:304-313`), затем отдельными запросами идут строки (`:335-346`) и `COUNT(*)` (`:347-355`) — три чтения без общей транзакции, `total` и `rows` могут оказаться из разных пересчётов;
- пересчёт делает `DELETE` + `INSERT` в одной транзакции SQLite (`:182-283`); в режиме WAL читатели видят прежнее состояние до коммита, поэтому «пустого рейтинга» посреди пересчёта нет — но только пока пересчёт именно один и именно транзакционный; `as_of=date.today()` меняет период каждый день, старые периоды в `running_athlete_rating` не удаляются (накапливаются);
- `get_rating_me_row` считает место внутри пола отдельным `COUNT` по живой таблице (`:405-423`), то есть может не совпасть с `rows` в ответе;
- если читать **PostgreSQL** во время `scoring.recalculate`: MVCC даёт согласованное «до»/«после», но `save_results` (`DELETE` + `COPY`) и `dedup.py` меняют `result` в разные моменты — при чтении «живых» `result` между ними вы увидите полу-обновлённую картину (дистанция уже без дублей, соседняя ещё с дублями). `run.py` коммитит раз в старт, поэтому видны промежуточные состояния «часть стартов новая, часть старая».

Версий/снимков рейтинга нет: `FORMULA_VERSION` — это версия формулы, не версия данных.

## 2. LLM и агентный слой: что есть на самом деле

### 2.1. Агент-ремонтник (единственный «настоящий»)

`python agent_queue.py process <issue_id> [--agent gigachat_agent]` (`agent_queue.py:291-366`):
1. `claim` — атомарный `UPDATE ... WHERE status='new' AND assignee='agent'` (`:277-283`): защита от двух агентов на одну задачу.
2. `build_sandbox` (`:61-106`): копия `*.py` парсера и сохранённые ответы площадки из `data/raw`, без сети.
3. `run_child` (`:109-119`) — подпроцесс `subprocess.run(..., timeout=300)` (`CHILD_TIMEOUT_S`, `:38`): перезапуск коннектора в песочнице, «до правки».
4. `agent.solve` (`evals/agents/gigachat_agent.py:240-302`): задача `stage == "fetch"` эскалируется без LLM (`:242-244`); иначе цикл до `MAX_ATTEMPTS = 4` (`:26`): `llm.chat` -> разбор ответа -> `tools.run_checks(edits)` (ещё один подпроцесс до 300 с) -> обратная связь модели.
5. После агента — независимая финальная `run_checks` (`agent_queue.py:349`) и запись в `agent_run`/`issue`.

Вызовов LLM: **1-4 `chat` на задачу** (каждый до 3 повторов на 429/5xx с паузами 5/10 с, `evals/agents/gigachat_client.py:110-119`, таймаут 120 с) + OAuth-токен на клиента (кеш на 25 мин, `:71-81`). Ответы кешируются на диск по хешу запроса (`:105-108`). Подпроцессов проверки: 1 (baseline) + до 4 (по попытке) + 1 (финал) = до 6, каждый до 5 минут. Реальное время на задачу — минуты, худший случай — десятки минут. Всё синхронно, `requests`, один процесс.

Что агент умеет: **чинить существующий коннектор** по упавшим проверкам или предложить `known_exception` / эскалацию. Новую площадку он не создаёт.

Применение: после `approve` человеком — `apply_approved` (`agent_queue.py:631-708`): `git worktree`, повторный запуск, коммит, `push`, PR. Это уже не LLM.

Конкуренция: `claim` защищает от двух обработчиков одной задачи; параллельный запуск разных задач ничем не ограничен (лимит токенов GigaChat никто не считает).

### 2.2. Оценка спортсмена (`app/services/agent_service.py`)

Не про парсер. Эндпоинт `POST` оценки спортсмена: метрики из SQLite -> GigaChat (2 вызова `httpx.AsyncClient`: токен + чат, `agent_service.py:51-93`) -> кеш в `athlete_assessment_cache` (`:238`) -> при ошибке локальная заглушка `generate_local_expert_assessment` (`:95`). `async def`, но SQLite синхронный (см. 1.4).

### 2.3. MCP-оркестратор и validator (`app/mcp_agent/`) — заготовка, не в конвейере

- `ParsingAgentOrchestrator.run_pipeline_with_ai_fallback` (`orchestrator.py:107-179`) нигде не вызывается из `run.py` и API; единственный вызов — `test_mcp_agent.py`.
- `MCPAgentClientStub` (`mcp_client.py:43+`) только логирует вызовы («Playwright», «llm_extract_table» — в docstring); реального MCP-транспорта нет.
- `sync_postgres_issue` (`orchestrator.py:25-69`) **записывает в PG выдуманные** `patch` для `rr_platform.py` и отчёт `ok: True` с токенами `1120/340` — карточка в `/agent-review` выглядит как настоящее предложение агента.
- `validator.validate_protocol_data` (`validator.py:23+`) — второй набор проверок NULL/монотонности, дублирующий `store.checks` (`store.py:109`); пороги 5 % NULL.
- Внутри свой SQLite (`app/db.py`) и свой fingerprint (`orchestrator.py:18-21`), отличный от `parser_running/db.py:209` — один и тот же сбой получит два разных ключа в двух базах.

### 2.4. `parse_url.py` — «синтез коннектора» (вход для исследователя гибкого парсера)

- Один вызов GigaChat (`parse_url.py:32-138`, `asyncio.run` в `:173`), модель `GigaChat-2-Pro`.
- **Промпт не содержит реальной страницы**: в нём вшита придуманная разметка `<table class="results-t">` с 10 колонками (`:46-90`). Реальный HTML URL модель не видит.
- Постобработка кода — регулярки и замены `"!= 5" -> "< 5"` (`:122-126`); при невалидном ответе подставляется шаблонный парсер (`:183-211`).
- Результат — класс с `parse_results(self, html)` (`:191`), который **не соответствует контракту коннектора** (`competitions/races/results`, `store.py:3-9`) и не подключается к `run.py`.
- Отчёт в БД `task_check.ok = True` пишется без какого-либо запуска (`:258-267`); `DELETE FROM issue/agent_run/agent_review` по fingerprint (`:233-235`) стирает историю предыдущих попыток; тестовый файл пишется в текущий каталог (`:277`).
- Список «поддерживаемых платформ» `SUPPORTED_PLATFORMS` (`:23-29`) расходится с реальным реестром `CONNECTORS` (`run.py:23-24`): там `results.zone`, `grom.club`, `heroleague.ru`, а реально есть `results.runc.run`, `grom.place`.

## 4. Идемпотентность, повторы, кеш, ошибки, наблюдаемость, конкуренция

**Идемпотентность.**
- Хорошо: `competition`/`race` — upsert по `(source_id, external_id)` и `(competition_id, external_id)` (`store.py:34-60`), `raw` — по `(source_id, request_key, content_hash)` (`db.py:83`), `issue` — по `fingerprint` (`db.py:216`), `source` — по имени.
- `result` — `DELETE` по `race_id` + `COPY` (`store.py:74-84`): повтор даёт тот же результат, пока запуск один. Естественного уникального ключа на `result` нет.
- Состояние «что уже собрано в этом запуске» нигде не хранится: возобновление работает только за счёт файлового кеша и повторного прохода по всему списку.

**Повторы.**
- `http_cache.get`: 3 попытки только на `Timeout`/`ConnectionError`, паузы 5 и 10 с (`:32-41`); **5xx и 429 не ретраятся** (`raise_for_status` выбрасывает `HTTPError`, которого нет в `except`). `RRClient._call`: 3 попытки без паузы между ними (`rr_platform.py:41-49`). `Retry-After` нигде не читается.
- LLM: 3 повтора на 429/5xx (`gigachat_client.py:110-119`).
- Повторов на уровне «дистанция упала -> попробовать позже» нет: ошибка превращается в `issue` и строку отчёта (`run.py:100-125`).

**Кеш HTTP.** Файл `data/raw/<источник>/<sha1(url)>.html|json`, при наличии возвращается всегда (`http_cache.py:29`, `rr_platform.py:38`). Не кешируются только список стартов RR (`rr_platform.py:59`) и ответы с 404/ошибками. TTL, ревалидации по ETag, различения «старт идёт сейчас / старт закончился давно» нет. Следствие: предварительный протокол (`isFinalProtocol=false`) навсегда останется предварительным, пока не удалят файл.

**Ошибки.** `try/except` на уровне старта и дистанции (`run.py:79-125`): исключение превращается в `issue` + `stats[...]`, обработка идёт дальше. Хорошо: один плохой протокол не роняет прогон. Плохо: ошибка БД внутри транзакции старта (`con.execute` падает) приведёт к aborted-транзакции и каскаду ошибок на остальных дистанциях старта — `con.rollback()` в `run.py` нигде не вызывается.

**Транзакции.** Соединение одно, `commit()` — раз на старт (`run.py:165`) и в конце `report_issue`-вызовов; всё, что между, включая сетевые запросы `conn.results()`, происходит внутри открытой транзакции. `db.connect()` при каждом подключении выполняет весь DDL (`db.py:185-189`) — это же делает `app/agent_review.py:_con()` на каждый запрос.

**Наблюдаемость.** `print` итогового JSON в конце (`run.py:67`), файл `data/report_<площадка>.json` после завершения (`:167-169`), строки в `issue`. Нет прогресса во время работы, нет логов с контекстом, нет метрик, нет записи «запуск N: когда начался/закончился/чем завершился». Узнать, что `run.py` завис на медленном `runc`, можно только по `ps`.

**Конкуренция двух запусков.** Не защищена: ни advisory lock, ни таблицы запусков. Что происходит, если одновременно запустить `run.py --source runc` дважды (или `run.py` и `dedup.py`):
- `DELETE FROM result WHERE race_id = X` во втором запуске ждёт блокировок первого, а после коммита первого его `DELETE` (READ COMMITTED, снимок на момент начала оператора) не увидит строк, вставленных первым, и вставит свои — **дубли строк результатов** по дистанции; уникального ограничения нет.
- `dedup.py` обнуляет `duplicate_of` по всей таблице `result` (`:82`) и держит блокировки до коммита; параллельный `save_results` на тех же строках встанет в очередь на всё время дедупа.
- `agent_queue.claim` защищает только агента, не парсер.

Это выводы из чтения кода; на живой базе поведение дублей стоит подтвердить тестом из двух процессов на одной дистанции.
