# Спецификация: баллы и рейтинг (бег)

| | |
|---|---|
| **Статус** | Черновик, 2026-10-27 |
| **Охват** | Бег: шоссе и стадион. Лыжи, триатлон и трейл — отдельные спеки по тем же швам |
| **Опирается на** | ТЗ заказчика (раздел «Бег дорожка и шоссе»), SPEC руководителя v1.2 §7, §9.1, §9.5–§9.7, [parser-db-spec.md](parser-db-spec.md) |
| **Где ⏳** | Правило ждёт подтверждения. Реализуется как настройка со значением по умолчанию из этого документа |

---

## Problem Statement

Рейтинг бегунов Сбера сейчас ведёт капитан бега вручную в Google-таблице: «желающие сами заполняют, я корректирую по формулам». Это медленно, неполно (в рейтинг попадает только тот, кто сам внёс старт) и непрозрачно для участника: не видно, откуда взялись его баллы.

Парсер уже собирает протоколы (около 288 тыс. результатов после дедупа с 4 площадок), но между протоколом и рейтингом ничего нет:
- результат не превращается в баллы;
- нет таблицы нормативов по годам;
- классификатор дистанций не совпадает с правилами SPEC (±2% без деления на шоссе и стадион; нет синонимов «паркран», «десятка»; нет суточного бега);
- нет правил, какое время брать (чистое или грязное), что делать со стартами прошлого года и с полной ничьей в рейтинге.

## Solution

Два чистых вычисления поверх базы, которые можно пересобрать в любой момент без перепарсинга:

1. **Баллы за результат.** Для каждого финишёра на зачётной дистанции: `норматив_сек / время_сек × 1000` (суточный бег: `км / норматив_км × 1000`). Каждый балл хранится с расшифровкой: класс дистанции, какой норматив и за какой год, какое время (чистое или грязное), формула с подставленными числами.
2. **Рейтинг за период.** Сумма баллов всех стартов спортсмена за период (по умолчанию скользящие 365 дней), только за то время, когда он был сотрудником. Места с понятными правилами при равенстве.

Сотрудник видит своё место и может проверить каждый балл. Капитан сверяет автоматический рейтинг со своей таблицей и видит расхождения с причинами. Заказчик меняет норматив или правило — рейтинг пересчитывается сам.

## User Stories

**Сотрудник (зритель рейтинга)**
1. As a сотрудник-бегун, I want видеть своё место в рейтинге бега за последние 365 дней, so that понимать, где я среди коллег.
2. As a сотрудник-бегун, I want видеть баллы за каждый свой старт, so that понимать, из чего сложилась сумма.
3. As a сотрудник-бегун, I want видеть формулу с подставленными числами (норматив, моё время, результат), so that проверить расчёт сам.
4. As a сотрудник-бегун, I want видеть, по какому времени посчитан старт (чистое или грязное), so that понимать, почему балл отличается от моих ожиданий.
5. As a сотрудник-бегун, I want чтобы 10 км по шоссе считались по нормативу 10 000 м, so that правило было одинаковым для всех.
6. As a сотрудник-бегун, I want чтобы «полумарафон», «21,1», «21,0975» и «21,195» считались одной дистанцией, so that название у организатора не лишало меня баллов.
7. As a сотрудник-бегун, I want чтобы паркран и «5 вёрст» засчитывались как 5000 м, so that регулярные субботние забеги шли в рейтинг.
8. As a сотрудник-бегун, I want видеть, что старт на нестандартной дистанции (15 км, 30 км, 2,5 км) не засчитан и почему, so that не думать, что результат потерялся.
9. As a сотрудник-бегун, I want получать больше 1000 баллов, если я быстрее норматива, so that сильный результат не обрезался.
10. As a сотрудник-бегун, I want чтобы засчитывались все мои старты, а не только лучшие, so that регулярное участие поощрялось.
11. As a сотрудник-бегун, I want чтобы при равной сумме выше был тот, у кого лучший одиночный старт, so that правило было понятным.
12. As a сотрудник-бегун, I want фильтровать рейтинг по полу и возрастной группе без изменения баллов, so that сравнивать себя с похожими.
13. As a сотрудник-бегун с суточным забегом, I want получать баллы по пройденным километрам, so that ультра тоже учитывалась.
14. As a сотрудник-бегун, I want чтобы сход (DNF), дисквалификация и неявка не давали баллов и не портили рейтинг, so that считались только финиши.
15. As a сотрудник, который пришёл в банк недавно, I want чтобы в рейтинг шли только старты с даты прихода, so that правило было одинаковым для всех.
16. As a уволившийся сотрудник, I want чтобы мои прошлые старты оставались в архиве, so that история не пропадала.

**Капитан бега**
17. As a капитан бега, I want сверить автоматический рейтинг со своей таблицей и получить список расхождений с причиной (формула / данные / правило не подтверждено), so that доверять системе и закрыть ручную таблицу.
18. As a капитан бега, I want видеть рейтинг на любую прошлую дату (срез), so that сравнивать с ранее опубликованными итогами.
19. As a капитан бега, I want видеть архив по календарным годам, so that подводить итоги года.
20. As a капитан бега, I want выгрузить рейтинг с расшифровкой баллов в Excel, so that работать с ним офлайн.
21. As a капитан бега, I want видеть список незачтённых стартов сотрудников с причиной, so that решать, назначать ли им класс вручную.

**Администратор (организатор)**
22. As a администратор, I want вести таблицу нормативов по годам (дистанция × пол), so that обновлять их, когда заказчик даст новые.
23. As a администратор, I want чтобы смена норматива сразу пересчитывала баллы и рейтинг, so that не запускать ничего вручную.
24. As a администратор, I want чтобы старая версия баллов сохранялась при смене формулы, so that можно было сравнить «до» и «после».
25. As a администратор, I want вручную назначить класс нестандартной дистанции или снять зачёт с дистанции, so that исправлять редкие случаи без программиста.
26. As a администратор, I want редактировать матрицу синонимов дистанций, so that добавлять новые названия организаторов.
27. As a администратор, I want переключать правило агрегации (все старты / лучшие N), so that быстро ответить заказчику, если он передумает.
28. As a администратор, I want переключать правило выбора времени (чистое, если есть / всегда официальное), so that не переписывать калькулятор при решении заказчика.
29. As a администратор, I want видеть, по какому году нормативов посчитан каждый старт, so that ловить старты из года без таблицы.

**DS / аналитик**
30. As a DS, I want golden-тесты по таблице нормативов ТЗ, so that любая ошибка формулы ловилась до релиза.
31. As a DS, I want сравнить автоматический рейтинг с таблицей капитана метриками (доля стартов с |Δ| ≤ 0,5, Spearman ρ, совпадение топ-10), so that количественно доказать качество в дипломе.
32. As a DS, I want сравнить рейтинг по «всем стартам» и по «лучшим 3», so that показать заказчику цену решения.
33. As a DS, I want видеть долю результатов, попавших в каждый класс, и долю незачётных, so that оценить классификатор.
34. As a DS, I want чтобы баллы считались для всех результатов, а не только сотрудников, so that показывать лидеров дистанции в карточке старта и проверять распределение баллов.
35. As a DS, I want чтобы дубли (зеркала одного старта) не давали баллы дважды, so that рейтинг не завышался.

**Разработчик бэкенда / фронтенда**
36. As a бэкенд-разработчик, I want один вызов «пересчитать» над базой, so that встраивать пересчёт в ночную задачу и в обработчик загрузки.
37. As a фронтенд-разработчик, I want получать расшифровку балла в готовом виде (формула с подставленными числами), so that не дублировать логику на клиенте.

## Implementation Decisions

### Модули

| Модуль | Что делает | Интерфейс |
|---|---|---|
| **Нормативы** | Хранит таблицу `год × класс × пол → значение` (сек; для 24 ч — км). Начальное наполнение — таблица ТЗ на 2026 год | `норматив(год, класс, пол) → значение + фактический год` |
| **Классификатор дистанций** | Название дистанции и старта + метры + дисциплина → зачётный класс или «незачётная» с причиной | `класс(название_дистанции, название_старта, метры, дисциплина) → класс | None, причина` |
| **Калькулятор баллов бега** | Чистая функция | `баллы(результат, контекст дистанции, нормативы, настройки) → баллы + расшифровка` |
| **Сборщик рейтинга** | Баллы + привязки к спортсменам + периоды сотрудника → места | `рейтинг(период, дата среза, настройки) → строки рейтинга` |
| **Пересчёт** | Обходит базу, пишет баллы и рейтинг, идемпотентен | `пересчитать(база, версия формулы)` |
| **Сверка с эталоном** | Таблица капитана → отчёт расхождений и метрики | `сверить(эталон, рейтинг) → отчёт` |

Калькулятор — это реестр «вид спорта → калькулятор». Лыжи, триатлон и трейл позже добавятся как ещё три калькулятора с тем же интерфейсом (SPEC §9: «все калькуляторы — чистые функции»).

### Классы дистанций
- Зачётные: 60, 100, 200, 400, 800, 1000, 1500 м, миля (1609 м), 3000, 5000, 10 000 м, 21,1 км, 42,2 км, 100 км, 24 ч.
- **Порядок определения** (SPEC §7):
  1. ручное назначение администратора — главнее всего;
  2. матрица синонимов по названию дистанции и старта (правит администратор): «полумарафон | 21,1 | 21,0975 | 21,195 | 21,18» → 21,1 км; «марафон | 42,2 | 42,195» → 42,2 км; «десятка | 10 км» → 10 000; «5 км | пятёрка | 5 вёрст | паркран» → 5000; «сутки | 24 часа» → 24 ч;
  3. метры: **±1% для шоссе, точное совпадение для стадиона**;
  4. иначе — незачётная, причина записывается.
- **Дисциплина** (шоссе / стадион): из источника, иначе по ключевым словам («стадион», «манеж», «дорожка», «track» → стадион), иначе по длине: от 21,1 км всегда шоссе; короче — шоссе ⏳. Нужна только для допуска: класс норматива один (10 км шоссе = 10 000 м стадион).
- Сейчас в базе все зачётные дистанции укладываются в ±1% (например, 21 000 м, 21 200 м, 42 400 м), поэтому сужение с ±2% до ±1% ни одной строки не убирает. Самые частые незачётные: 2,5; 6; 30; 2; 12 км.

### Баллы
- `баллы = норматив_сек / время_сек × 1000`; для 24 ч — `км / норматив_км × 1000`.
- **Ограничения сверху нет**: быстрее норматива — больше 1000.
- **Баллы получают** только строки со статусом FIN, не являющиеся дублем (`duplicate_of` пуст), на зачётной дистанции, с известным полом и временем.
  - DNF, DSQ, DNS, LAP — без баллов.
  - **NC (вне зачёта)** — без баллов по умолчанию ⏳: время у них настоящее, но организатор их не ранжирует.
  - Без пола — без баллов, в модерацию (сейчас таких зачётных финишёров 0).
- **Какое время:** чистое, если есть, иначе грязное (SPEC §7) ⏳ команда, не заказчик. В расшифровке — `time_kind`. Сейчас чистого нет у 771 зачётного финишёра; у 51 тыс. места расставлены по грязному (элита runc, часть RR), но баллы всё равно по чистому.
- **Год норматива:** год даты старта; если таблицы на этот год нет — ближайший более ранний; если и его нет — самый ранний из имеющихся ⏳. Сейчас 18,6 тыс. результатов 2025 года будут посчитаны по нормативам 2026; это видно в расшифровке.
- **Спринт с финалом** (E28): берётся время из протокола (у финалистов — время финала) ⏳ заказчик.
- **Эстафеты** в беге не считаются, парсер их пропускает ⏳.
- **Несколько дистанций на одном старте**: засчитываются все ⏳ (как в лыжах).
- Храним полную точность, показываем до 0,01.

**Расшифровка** (форма, которую получает фронтенд):

```
{ sport: "run", class: "10000m", discipline: "road", gender: "M",
  norm_value: 1760, norm_year: 2026, norm_year_requested: 2025,
  time_kind: "chip", time_s: 2400, formula: "1760 / 2400 × 1000",
  points: 733.33, formula_version: "run-v1" }
```

### Рейтинг
- **Агрегация:** сумма всех стартов за период (`sum_all`, решение заказчика). Режим `sum_best_n` есть в настройках для сравнения, но по умолчанию выключен.
- **Кто попадает:** результаты, привязанные к спортсмену (привязка `auto` или `confirmed`), который на дату старта был сотрудником (`employee_since..employee_until`).
- **Равенство:** больше лучший одиночный старт → больше стартов → общее место (схема «1, 1, 3»).
- **Периоды:**
  - `rolling` — по умолчанию; старты с датой в `(сегодня − 365 дней, сегодня]`;
  - срез на дату — то же окно до выбранной даты;
  - календарный год — архив.
- **Пол:** один общий рейтинг (баллы уже нормированы по полу), пол — фильтр ⏳. Возрастные группы фильтра: 18–29, 30–39, 40–49, 50–59, 60+ ⏳.
- **Фильтры** не меняют баллы, места пересчитываются внутри выборки.

### Схема (дополнение к parser-db-spec §4)
- `norm(year, distance_class, gender, value, unit)` — нормативы.
- `distance_synonym(pattern, distance_class)`, ручное переназначение класса на `race` (`class_source = auto | manual`) и поле `discipline`.
- `score(result_id, formula_version, points, breakdown)` — ключ `(result_id, formula_version)`: новая формула не затирает старые баллы.
- `rating_entry(sport, period_key, athlete_id, rank, points, starts, best_points)`.
- `setting(key, value)` — агрегация, выбор времени, правило года норматива, допуски.

`score` и `rating_entry` — вычисляемые слои: их можно удалить и пересобрать из `result` в любой момент.

### Зависимость от сопоставления спортсменов
Рейтинг строится по спортсменам, а сопоставление «строка протокола → спортсмен» — отдельная спека. Пока его нет, сборщик рейтинга получает привязки на входе. Для демо используем временные привязки: строки сберовских клубов, склеенные по точному ФИО + году рождения (или возрасту ±1). В отчёте они помечены как временные.

## Testing Decisions

**Хороший тест** проверяет внешнее поведение на шве: «вот результат и дистанция — вот баллы и расшифровка», «вот набор баллов — вот места». Он не проверяет, как устроены внутренние функции, и не ломается от рефакторинга.

**Швы** (два):
1. **Балл за результат** — калькулятор вместе с классификатором и нормативами. На вход — поля строки протокола и дистанции, как они лежат в базе; на выход — баллы и расшифровка. Здесь живут все правила одного старта.
2. **Пересчёт базы → рейтинг** — маленькая тестовая база (синтетические спортсмены и старты, выдуманные фамилии) → строки рейтинга. Здесь живут агрегация, периоды, сотрудничество, равенства, идемпотентность.

**Наборы:**

| Набор | Шов | Что | Порог |
|---|---|---|---|
| G1. Golden по ТЗ | 1 | Все строки таблицы нормативов × пол + примеры: 10 км шоссе → 10 000; паркран; 21,0975; сутки; быстрее норматива (1047,62); год без таблицы | точно до 0,01 |
| G9. Классификатор | 1 | Все уникальные названия и длины дистанций из нашей базы, размеченные вручную | доля верных; список ошибочно незачётных |
| Свойства | 1 | Быстрее → больше баллов; DNF/NC/дубль → нет баллов; без пола → модерация | — |
| Рейтинг | 2 | Сумма; равенства «1, 1, 3»; граница окна 365 дней; приход и уход сотрудника; повторный пересчёт ничего не меняет; смена норматива меняет только затронутые баллы | точно |
| G2. Таблица капитана бега | 1 и 2 | Его Google-таблица ⏳ (SPEC §13 №11) | старт: |Δ| ≤ 0,5; рейтинг: Spearman ρ и совпадение топ-10, каждое расхождение с причиной |

**Аналоги в репозитории:**
- эталонные проверки нормализации в регрессии evals — тот же стиль «вход → ожидаемое»;
- проверки качества 1–6 при записи в базу — для инвариантов («у всех финишёров есть баллы или причина, почему нет»);
- оценка дедупа по `participantId` — образец отчёта «метрика + список расхождений».

## Out of Scope
- Лыжи (с биатлоном и очками Russialoppet), триатлон, трейл — свои калькуляторы по тем же швам, отдельные спеки (SPEC §9.2–§9.4).
- Сопоставление строк протокола со спортсменами и признак «сотрудник» — отдельная спека; здесь только вход.
- Возрастные коэффициенты WMA (бэклог SPEC).
- Эстафеты в беге.
- Экраны, API, выгрузка в Excel — здесь только данные, которые им нужны (расшифровка, строки рейтинга).
- Командный зачёт по подразделениям.

| 4 | Спринт с финалом: время финала или лучшее из забегов | заказчик | время из протокола |
| 5 | Финишёры вне зачёта (NC) | заказчик | без баллов |
| 6 | Допуск ±1% / точно — решение команды, заказчиком не подтверждено | заказчик | как в SPEC |
| 7 | Общий рейтинг с фильтром по полу или два раздельных | заказчик | общий + фильтр |
| 8 | Несколько дистанций одного старта — все в зачёт | заказчик | все |
| 9 | Эстафеты в беге | заказчик | не считаем |

**Порядок работ:** нормативы и классификатор → калькулятор с G1 и G9 → пересчёт и рейтинг на временных привязках → сверка с G2, когда придёт таблица. Первые два шага не зависят ни от сопоставления спортсменов, ни от ответов заказчика.

**Устаревшее в parser-db-spec §10:** вопрос 1 (агрегация и сезон) закрыт перепиской — сумма всех стартов, 365 дней. Вопрос 3 частично закрыт матрицей синонимов.
