# Этап 0: единая PostgreSQL и локальная инфраструктура

## Что входит

PostgreSQL 16, Alembic, перенос сохранённых данных SQLite, PostgreSQL API, multi-stage Dockerfile (React + Python в одном runtime-образе), Compose и CI. Схема создаётся отдельным сервисом `migrate`; API не выполняет DDL при старте. API стартует после успешного завершения миграции. Проверки `/health/live` и `/health/ready` зарегистрированы перед SPA fallback; Compose использует readiness.

Архитектурные ориентиры: [gap, задача 0](spec/SPEC-v1.3-gap.md), [BACKEND_GUIDE](review/BACKEND_GUIDE.md), [PIPELINE_ARCHITECTURE](review/PIPELINE_ARCHITECTURE.md), [актуальная SPEC](spec/SPEC.md). Очередь procrastinate, worker, публикация версий рейтинга и облачный деплой не входят в этап 0. Рабочая база интеграции — актуальная ветка `dev`: сохранены её пользователи `app_user`, Argon2, регистрация со статусом pending, роли user/captain/admin, проверки статуса сотрудника, обращения, модерация заявок и ограничения выдачи ПДн. Это не заявление о полной реализации разделов auth/ПДн SPEC: токены пока HMAC, отзыв хранится в памяти процесса, SMTP-сброс пароля, rate-limit, постоянное хранение сессий и весь набор требований безопасности не подтверждены. Публичный деплой в этой работе не выполняется.

## Оставшиеся ограничения унаследованной auth

Следующие особенности перенесены из `dev` и не закрыты инфраструктурным этапом:

- Backend регистрации пока не отклоняет `consent=false`; значение по умолчанию в запросе также `true`.
- Проверка роли капитана есть, ограничения капитана по видам спорта пока отсутствуют.
- Одобрение заявки с привязкой к спортсмену может заменить `not_employee` на `presumed`; запрет доступа по статусу сотрудника поэтому требует доработки процесса модерации.
- Отзыв HMAC-токена хранится в памяти одного процесса и не переживает перезапуск; постоянные сессии не реализованы.

Проверки этапа 0 подтверждают работу перенесённых сценариев на PostgreSQL, но не полную безопасность auth, согласий и разграничения доступа.

## Локальный Compose

1. Скопируйте `env.example` в `.env`.
2. Задайте независимые случайные `POSTGRES_PASSWORD` и `AUTH_SECRET_KEY`. Пароль PostgreSQL не имеет значения по умолчанию. `AUTH_SECRET_KEY` нужен для стабильной подписи токенов при перезапуске; список отозванных токенов пока остаётся в памяти процесса.
3. Укажите `DATABASE_URL` для хостовых команд, с `127.0.0.1` и `DB_PORT`. Пароли внутри URL должны быть percent-encoded; само значение `POSTGRES_PASSWORD` задаётся без URL-кодирования. Для пароля с зарезервированными символами задайте `COMPOSE_DATABASE_URL` явно. В контейнерах эта отдельная переменная указывает на `db:5432`; существующий хостовый `DATABASE_URL` не меняется.
4. Запустите `docker compose up --build -d` и проверьте `docker compose ps`.
5. Откройте `http://127.0.0.1:8000/health/ready` и `/`. Для другого локального порта задайте `APP_PORT`.

`docker compose logs migrate api` показывает результат миграции и запуска. `docker compose down` останавливает стек и сохраняет именованный volume. Не удаляйте volume с данными при обновлении. PostgreSQL и API публикуются только на loopback. Миграции и API используют один образ; runtime работает от непривилегированного пользователя. Docker context ограничен белым списком: `.env`, базы, raw и локальные зависимости исключены.

Python на хосте: `pip install -r requirements-dev.txt`, `docker compose up -d db`, `python -m alembic upgrade head`, затем `npm --prefix frontend ci`, `npm --prefix frontend run build` и `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`. Настройки читаются `pydantic-settings` из окружения и корневого `.env`, окружение имеет приоритет. `DATABASE_URL` обязателен и допускает только PostgreSQL. Схемы `postgres://`, `postgresql://`, `postgresql+asyncpg://` нормализуются к `postgresql://` для синхронных клиентов; percent-encoded компоненты URL сохраняются. Async SQLAlchemy выбирает свой драйвер отдельно. Имена `DATABASE_URL`, `APP_HOST`, `APP_PORT`, `GIGACHAT_*` совместимы с прежними импортами. Проверка TLS GigaChat включена по умолчанию.

## Пользователи на чистой базе

Alembic не создаёт встроенные учётки. Вход использует записи `app_user` и Argon2-хэши. Регистрация в UI создаёт заявку со статусом pending; доступ появляется после одобрения. Для первого администратора локального стенда зарегистрируйте собственную учётку с уникальным паролем и один раз назначьте ей `role='admin', status='active'` через контролируемый доступ владельца базы. Проверьте точный username до изменения. Остальных пользователей одобряйте через очередь заявок.

Не используйте старый `scripts/init_users.py`: он создаёт известные демонстрационные пароли и может перезаписать существующие user/admin. Старые `scripts/migrate_*` не заменяют Alembic. Если нужен импорт SQLite, выполните его до регистрации первого пользователя: guard требует пустые бизнес-таблицы PostgreSQL.

## Одноразовый импорт SQLite

Сохраните резервную копию источника и целевой базы. Примените `alembic upgrade head` к новой пустой PostgreSQL; не направляйте импорт в существующую рабочую базу. Команда использует хостовый `DATABASE_URL`:

```bash
python -m app.pipeline.import_sqlite /absolute/path/to/running.db
```

SQLite открывается в `mode=ro`; согласованный снимок снимается SQLite backup API, включая активный WAL. Исходный файл не редактируется. Импорт переносит исходные таблицы, спортсменов, отдельную связь `result_athlete`, кэш оценок и сохранённые таблицы `rating_norm`, `rating_score`, `running_athlete_rating` при наличии. Готовые баллы, `rank`, период и `formula_version` копируются как есть, без повторного вычисления на текущую дату.

Импорт работает транзакционно и отклоняет непустую целевую базу; сверяет счётчики и контрольные суммы переносимых строк и связей. Отчёт и хэш снимка сохраняются в `migration_import`; повторный импорт того же снимка обрабатывается идемпотентно. Сохраните JSON-отчёт из stdout и проверьте совпадение числа спортсменов, результатов и связей, а также `rank` и баллов в рейтинге. Не запускайте переиндексацию спортсменов или пересчёт до проверки. При ошибке PostgreSQL-транзакция откатывается; источник остаётся неизменным.

Исторические parser CLI могут содержать старые точки инициализации схемы. Для этапа 0 владельцем структуры базы служит Alembic; не используйте старые bootstrap/migrate-скрипты поверх целевой схемы. Worker, автоматический сбор и пересчёт не запускаются Compose.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
# Укажите TEST_POSTGRES_ADMIN_URL в окружении; отдельная роль с CREATEDB.
python -m alembic heads
python -m pytest tests/stage0 tests/test_auth.py tests/test_athlete_fields.py tests/test_privacy_and_roles.py tests/test_requests_and_reports.py -q
npm --prefix frontend ci
npm --prefix frontend run build
```

PostgreSQL-тесты создают уникальные одноразовые базы и удаляют их после выполнения. Используйте отдельный локальный или CI-кластер; не выдавайте тестам административный доступ к рабочей базе. GitHub Actions поднимает PostgreSQL 16 для `tests/stage0` и адаптированных тестов auth, полей спортсмена, ПДн/ролей и заявок и выполняет TypeScript/Vite build отдельным заданием. Старые скрипты с SQLite не включены в приёмку Postgres-порта.

Наличие инфраструктуры и унаследованных механизмов auth/ролей/ПДн не означает готовность публичного развёртывания или полное соответствие SPEC. Ограничения токенов перечислены выше; аттестованное размещение не выполнялось.

Это проверки определения стека и кода. Docker CLI установлен, но Docker daemon недоступен (`dockerDesktopLinuxEngine` pipe отсутствует); сборка образа и `docker compose up` здесь не проверены. Удалённый GitHub Actions из этой рабочей копии не запускался. Результат PostgreSQL-тестов приведён ниже; он не заменяет проверку контейнерного запуска.
